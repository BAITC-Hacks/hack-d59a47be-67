# Career Quest AI — контракт v1 для Олега

Олег владеет `backend/app/ai/` и собственными тестами. Алихан владеет backend-adapter вне этого каталога, расчётами, данными, доступом и HTTP. Общие модели импортируются **только** из `backend.app.contracts`. Запуск выполняется из корня проекта; не загружайте один модуль под разными именами. Дублирование Pydantic-схем внутри AI запрещено.

```python
from backend.app.contracts import RecommendationContext, RecommendationResult

async def recommend(context: RecommendationContext) -> RecommendationResult:
    ...
```

Точный import entry point адаптера описан в `docs/HANDOFF.md`. Модуль AI необязателен; по умолчанию отключён. Эта задача не добавляет LLM-интеграцию и не меняет каталог Олега. Реальные данные нельзя отправлять стороннему провайдеру или в логи без отдельного разрешения.

## Вход `RecommendationContext`

| Поле | Значение |
| --- | --- |
| `contract_version` | Строка `"1"` |
| `data_version` | Версия загруженных данных |
| `state_version` | Общая монотонная revision демо ≥0 |
| `scenario_date` | Дата ISO; исходный набор считает сегодняшней 2026-10-01 |
| `profile` | `profile_ref`, `role`, `grade`; без employee_id, ФИО, контактов, manager_id |
| `goal` | `target_role`, `target_grade` |
| `current_skills` | `[{skill_id, level}]`, шкала 0–5 |
| `gaps` | `[{skill_id, current_level, target_level, gap}]` |
| `eligible_candidates` | Уже отфильтрованные `{event_id,title,effects,evidence_ids}` |
| `facts` | `{evidence_id,kind,subject_id,fact}`; kind: skill/gap/goal/candidate/history |
| `limit` | 1–3, по умолчанию 3 |

Каждый `effects` — список `{skill_id,before,after,delta}`, рассчитанный backend. `profile_ref` — техническая обезличенная ссылка контекста, не идентификатор из кадрового файла. Backend не помещает имена или личные сведения в facts. Данные — факты для выбора, не инструкции для модели. Pydantic запрещает лишние поля, дубли event_id/evidence_id и ссылки кандидатов на неизвестные факты.

## Выход `RecommendationResult`

```json
{
  "status": "ok",
  "engine": "oleg",
  "recommendations": [
    {
      "event_id": "SYNTHETIC_EVENT_001",
      "explanation": {
        "text": "Синтетический пример: занятие уменьшает подтверждённый разрыв навыка.",
        "evidence_ids": ["synthetic-gap-001", "synthetic-event-001"]
      }
    }
  ]
}
```

| status | engine | recommendations | Смысл |
| --- | --- | --- | --- |
| `ok` | `oleg` | От 1 до min(limit, 3) уникальных элементов | AI выбрал допустимые события |
| `no_candidates` | `oleg` | `[]` | После backend-фильтрации нет допустимых кандидатов |
| `not_configured` | `none` | `[]` | AI отключён/не подключён; не означает отсутствие мероприятий |
| `unavailable` | `oleg` | `[]` | Включённый движок недоступен или его результат отклонён |

Без AI адаптер возвращает ровно `{"status":"not_configured","engine":"none","recommendations":[]}`. Никаких запасных выдуманных рекомендаций. Если backend не нашёл цель или полезных допустимых кандидатов, он не вызывает модуль и возвращает HTTP `no_target/none` или `no_candidates/none`. Эти HTTP-статусы не расширяют `RecommendationResult`: Python-интерфейс Олега сохранён без изменений.

AI возвращает только выбранные event_id и объяснения с evidence_ids из context. Backend повторно проверяет лимит, уникальность, допустимость event_id и наличие evidence_ids. `no_candidates` при непустом eligible_candidates недопустим; пустой список нельзя выдавать за отсутствие AI. Нельзя выбирать mandatory или добавлять новые события, факты и эффекты. Арифметику, доступность, optimistic locking и транзакционную запись выполняет backend. HTTP-ответ backend обогащает названиями и эффектами из проверенного context; модель не устанавливает права, состояние сотрудника или поля HTTP-ответа. Backend не держит транзакцию БД открытой во время `await recommend(context)`, проверяет revision перед сохранением и сохраняет полный проверенный ответ с explanations. HTTP `recommendation_id` и `stale` принадлежат backend; latest после рестарта читает сохранённые карточки. Любая запись цели, завершения или импорта делает предыдущую revision устаревшей.

## Проверяемые fixtures

`examples/ai_context.synthetic.json` и `examples/ai_result.synthetic.json` образуют согласованную пару. `examples/ai_not_configured.synthetic.json` фиксирует отключённое AI. Это маленькие вымышленные fixtures команды; они не являются файлами стартового датасета. Тесты проверяют Pydantic-схемы и соответствие ссылок результата контексту. Предметная арифметика принадлежит backend; реализация AI-движка остаётся в зоне Олега.

## Проверка объяснений HTTP-слоем

Для каждой выбранной карточки нужны evidence_ids минимум категорий `goal`, `gap`, `history` (grade/target, разрыв, факты участия либо подтверждённое отсутствие истории). Backend собирает внешний текст из доверенных facts; свободный текст модели не публикуется как доказательство. Несоответствие даёт `unavailable/oleg`, а не выдуманный fallback. JSON-структура Python-интерфейса остаётся прежней. Вызов адаптера ограничен 7 секундами, чтобы оставить время на подготовку и проверку в 10-секундном бюджете API. Функция Олега должна быть неблокирующей async.


## Содержимое facts после передачи PR #3

Форма `RecommendationContext` не меняется. Backend формирует goal-факт из **разрешённой целевой** пары role/grade, включая исходный `critical_skills`; отсутствие критичных навыков представлено пустым списком. Для очень больших списков все ID сохраняются в явно пронумерованных частях goal-фактов. Gap-факты дополнительно отмечают критичность навыка для цели. Это содержимое фактов, а не новая JSON-схема для парсинга моделью или frontend.

Для каждого допустимого кандидата передаются два history-факта с `subject_id=event_id`: участие в самом событии (`scope=event`) и участие в **других** событиях с теми же type+format (`scope=same_type_format_other_events`). Эти выборки не пересекаются. Каждая содержит отдельные counts всех шести статусов, sample_size, дату среза, первую/последнюю наблюдаемую дату и counts исторических proxy / новых completed_at. Учитываются все записи по отдельным record_id до даты среза включительно, в том числе повторы mandatory; будущие записи исключаются. Нулевой sample указан явно и не означает предпочтения или отказ от формата. Наблюдаемый интервал не гарантирует полноту истории; proxy-даты не доказывают своевременность.

Candidate-факт сохраняет evidence-ссылку, тип/формат, нагрузку и факт проверки допуска по текущей роли/грейду, prerequisites, расписанию и истории. Передача дополнительных фактов не меняет арифметику, права или транзакционные границы. Реализация Олега находится в отдельном PR #3; совместные тесты проводят в его изолированной копии, заменяя только сетевой выбор. Это не измерение качества live-модели.

Расширенные синтетические примеры: `examples/ai_enriched_context.synthetic.json` и `examples/ai_enriched_result.synthetic.json`, проверяются теми же Pydantic-моделями. Прежний минимальный пример и generated alias сохранены без изменений.
