# Career Quest

Веб-приложение для развития сотрудника: профиль и карьерная цель → 1–3 рекомендации с объяснением → выполнение активности → обновлённые навыки и прогресс. HR видит частые дефициты навыков, сотрудников без актуального следующего шага и участие по мероприятиям.

Реализован кейс **Career Quest** из [исходного ТЗ](docs/requirements/original-spec.txt). Voice Router — другой кейс; валюта и награды опциональны. Публичных рейтингов сотрудников нет: они запрещены ТЗ. Выводы о мотивации по отсутствию истории не делаются. [Итоговый отчёт](docs/FINAL_REPORT.md) содержит проверенные сценарии, версии, измерения и ограничения; [сценарий защиты](frontend/JURY.md) — порядок демонстрации.

## Запуск одной командой

Нужен Docker с Compose. Для демонстрации настоящего AI создайте локальный `.env` по `.env.example` (существующий файл не перезаписывайте) и настройте:

```dotenv
AI_ENABLED=true
OPENAI_API_KEY=<ваш ключ только в локальном файле>
OPENAI_MODEL=gpt-4.1-mini-2025-04-14
AI_TIMEOUT_SECONDS=6.0
```

Из корня проекта:

```sh
docker compose --env-file .env -f compose.public.yaml up --build
```

Откройте **http://localhost:8080**. Кнопки «Кабинет сотрудника» и «Кабинет HR» создают настоящую серверную сессию в отдельной учебной копии. В ней используются собственные вымышленные профили, SQLite, расчёты и API. Переключение роли сохраняет вашу копию; другой браузер получает независимую базу. Ключ остаётся в backend и не входит в образ или JavaScript.

Без ключа можно выполнить `docker compose -f compose.public.yaml up --build` с `AI_ENABLED=false`: профиль, каталог, completion, HR и импорт работают, но **это не проверка AI-подбора**. При ошибке модели интерфейс показывает недоступность и ручной повтор; готовые рекомендации вместо ошибки не подставляются.

Учебные данные временные. Обычный restart того же контейнера сохраняет их; удаление/пересоздание контейнера public-режима может их потерять. Остановка: `docker compose -f compose.public.yaml down`. Эта конфигурация слушает только localhost; постоянный публичный хостинг не требуется для локальной приёмки.

## Что показать

1. Открыть кабинет сотрудника: роль/грейд, цель, текущие навыки, разрывы и история.
2. Нажать «Подобрать шаги». Проверить 1–3 карточки с целью, полезным навыком, требованиями уровня, историей и доступностью активности.
3. Открыть предварительный результат, подтвердить завершение вымышленного мероприятия. Навык и прогресс пересчитываются на сервере; история сохраняется, прежние рекомендации становятся устаревшими.
4. Перейти в HR: проверить дефициты, участие и отдельные причины отсутствия актуальной рекомендации. Отсутствие истории не трактуется как отсутствие мотивации; достигнутая цель не считается ошибкой AI.
5. В учебной копии скачать примеры JSON/CSV и импортировать оба файла: проверка → подтверждение. Количество сотрудников изменится с 3 до 6; во втором браузере останется 3.

## Исходный кит и профили жюри

Исходные данные организаторов не находятся в Git и не загружаются в публичную учебную копию. Примеры public-режима используют собственные идентификаторы; профили жюри проверяются на **частном сервере с каталогом исходного кита**. Подготовка выполняется один раз по [HANDOFF](docs/HANDOFF.md): установить Python 3.12/dependencies, импортировать четыре файла (`skills.json`, `events.json`, `employees.json`, `activity_history.csv`), создать HR и employee accounts со скрытым вводом пароля.

После подготовки среды из `frontend/`:

```sh
pnpm install --frozen-lockfile
pnpm start
```

Одна команда `pnpm start` запускает UI и API после установки зависимостей/подготовки данных. Нужны Node.js 22.12+, pnpm 11.25.0 и корневая `.venv`; используются существующие `.env` и `DATABASE_PATH`. Вход по личным учётным данным; дополнительный JSON профилей и CSV истории жюри загружаются HR совместно через preview/commit. Частично неверная партия не записывается. Новые employee_id/record_id добавляются, изменённые существующие записи отклоняются; исходные baseline и история сохраняются.

Частный Docker-вариант — `docker compose up --build`, UI/API на `http://localhost:8000`, постоянный volume `sqlite_data`; первоначальная загрузка данных и создание accounts описаны в HANDOFF. Не включайте `PUBLIC_DEMO_MODE` для базы кита. Не передавайте ограниченные данные внешнему AI без разрешения организаторов; наши live-проверки используют только собственные синтетические fixtures.

`pnpm start:demo` создаёт локальную синтетическую базу и случайные accounts, но принудительно выключает AI. Кнопка «Посмотреть демо» частного интерфейса показывает готовые браузерные ответы. Эти режимы явно обозначены и не подменяют проверку настоящей модели.

## Как устроено

React/TypeScript обращается к FastAPI через `/api` на том же origin. SQLite хранит исходные записи, accounts/сессии, импорт, завершения и полные карточки рекомендаций. Docker собирает frontend и backend в один непривилегированный образ; приложение использует один процесс.

Сервер восстанавливает навыки из baseline и завершений после оценки, учитывает gain/max_level и не снижает уже достигнутый уровень. Он выбирает допустимые мероприятия по роли/грейду, требованиям, расписанию и истории. AI получает подготовленный контекст, выбирает только 1–3 допустимых ID; структурная и смысловая проверка запрещает чужие ID и неподтверждённые основания. Объяснения формируются из связанных серверных фактов, а не свободного текста модели.

HR использует тот же срез данных: частоту разрывов с явным знаменателем, участие по статусам и причины отсутствия актуального шага. Неполученный подбор, устаревший результат, отказ AI, отключённая модель, отсутствие цели и отсутствие кандидатов различаются. HR-запрос сам не вызывает модель. Исторические даты обозначены как приблизительные; по ним нельзя обещать соблюдение сроков.

Права employee/HR, Origin/CSRF и версия данных проверяются сервером. Завершение с тем же Idempotency-Key и телом возвращает сохранённый ответ без двойного начисления, в том числе при исчерпанной публичной квоте; новое действие остаётся ограниченным. Public-режим разрешает переключение ролей только внутри собственной вымышленной копии и не даёт доступ к частной базе.

## Проверки

После установки `requirements-dev.lock` в Python 3.12 venv:

```sh
make check
.venv/bin/python -m pytest backend/tests/oleg_backend_handoff_acceptance.py -q
.venv/bin/python scripts/smoke.py --ai
.venv/bin/python scripts/check_container.py --require-ai
pnpm --dir frontend test
pnpm --dir frontend build
pnpm --dir frontend format:check
```

Обычные тесты не используют ключ и сеть; Docker-команда требует Docker и скачивает зависимости при необходимости. Реальная оценка AI запускается отдельно и отправляет только собственные fixtures:

```sh
.venv/bin/python -m backend.app.ai.latency_evaluation --live --env-file .env --rounds 3
```

Это 9 запросов к провайдеру. Без `--live` CLI проверяет fixtures без сети. ТЗ допускает UI до 2 s и AI до 10 s; внутренний deadline AI 6 s ограничивает ожидание, но не гарантирует успех внешнего сервиса. Конкретные измерения и все неуспешные попытки указаны в отчёте; нагрузочный SLA не заявляется. GitHub CI имеет известную billing lock: локальные результаты не выдаются за выполненные GitHub jobs.
