# Career Quest — пространство карьерного развития команды 67

AI-навигатор развития сотрудника для HackAlem AI / Halyk Bank. Целевой сценарий: профиль → обоснованный следующий шаг → выполнение → обновлённые навыки; для HR предусмотрены профили, импорт и аналитика развития. Реализованные части и оставшиеся пробелы перечислены ниже.

**Текущий статус:** в ветке `feat/product-ready` объединены интерфейс Батыра, backend Алихана и AI-модуль Олега. Работают вход, профиль/цель, серверные навыки и прогресс, каталог, preview и идемпотентное завершение, история, импорт JSON+CSV и HR-аналитика пробелов/участия. Подбор реализован через настоящий AI adapter с проверкой кандидатов и фактов. **Live AI в этой сборке пока не проверен: нужен секретный `OPENAI_API_KEY` на сервере; без него AI выключен и интерфейс честно сообщает об этом.**

Публичный режим создаёт каждому посетителю отдельную временную копию собственных вымышленных данных. Реальные API, SQLite, расчёты и импорт используются и в этом режиме; подготовленные браузерные ответы к нему не относятся. [Бесплатный Render и публичный запуск](docs/PUBLIC_DEPLOYMENT.md) подготовлены; постоянная публикация требует входа владельца в Render и доступа к приватному репозиторию. Docker-образ этой общей версии ещё не собирался в данном окружении.

**Временный публичный просмотр (23.09.2026):** [открыть Career Quest](https://assurance-elimination-reviewer-favour.trycloudflare.com). Проверены HTTPS-вход, каталог/preview/завершение, изоляция двух посетителей и импорт трёх профилей. Ссылка работает только пока этот компьютер и туннель включены; это не постоянный хостинг. AI здесь отключён.

**Роли команды:** Алихан — backend/данные/API/доступ/интеграция/деплой; Олег — `backend/app/ai/` и свои тесты; Батыр — `frontend/`. Единственный действующий контракт — [Python-модели](backend/app/contracts.py), [HTTP](contracts/API.md), [AI](contracts/AI_CONTRACT.md). По поручению владельца задачи оставшиеся части интегрированы совместно. Ниже сохранены результаты архитектурного этапа; текущие возможности описаны прежде них.

## Технический отбор — проверка для жюри

Актуальные критерии владельца задачи: **функциональность 20, техническая реализация 25, документация 20, воспроизводимость 20, надёжность и безопасность 15**. [Таблица подтверждений и пробелов](frontend/JURY.md) следует этой шкале; баллы себе команда не выставляет. При ограничении в пять часов приоритет — проверяемый основной сценарий, импорт и воспроизводимый запуск.

Самый короткий запуск открытой учебной версии из корня (требуется Docker с Compose):

```sh
docker compose -f compose.public.yaml up --build
```

Открыть **http://localhost:8080** → «Кабинет сотрудника» или «Кабинет HR». Пароли не требуются: каждый браузер получает отдельные вымышленные данные и настоящую серверную сессию. HR может скачать примеры трёх новых профилей и истории, загрузить оба файла через «Импорт», проверить и подтвердить запись. После импорта в его копии будет шесть сотрудников; чужие копии не изменятся. Примеры подготовлены для публичного каталога, исходный кит организаторов не опубликован.

Для бесплатной постоянной ссылки используется [render.yaml](render.yaml): один Docker-сервис **Free**, без платной БД и диска. После простоя сервис засыпает, а при перезапуске его временная SQLite теряется. Новая сессия получает исходные учебные данные. [Порядок публикации, ограничения и проверка](docs/PUBLIC_DEPLOYMENT.md).

Для проверки настоящего backend на вымышленных входных данных нужны **Python 3.12, Node.js 22.12+ и pnpm 11.25.0**. Из корня репозитория в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.lock
cd frontend
pnpm install --frozen-lockfile
pnpm start:demo
```

В Linux/macOS первые две команды: `python3.12 -m venv .venv` и `.venv/bin/python -m pip install -r requirements-dev.lock`; остальные те же. Открыть `http://127.0.0.1:5173`, войти обычной формой под сотрудником или HR с локальными случайными учётными данными из `frontend/.local-demo.json`. База `frontend/.qa/demo.sqlite3` сохраняет результат повторных запусков; исходный датасет не нужен для этой проверки.

**Проверочный путь:** сотрудник → каталог → preview активности → подтверждение завершения → изменение навыков/прогресса → история после перезагрузки; HR → JSON+CSV → проверка → подтверждение → новый профиль. [Подробный сценарий](frontend/JURY.md#проверить-настоящую-запись-результата). `pnpm test` и `pnpm build` запускаются из `frontend/`; HTTP smoke — из корня `.venv/bin/python frontend/scripts/test-live.py` (Windows: `.\.venv\Scripts\python.exe`).

**Различие режимов:** `start:demo` использует настоящий API/SQLite на синтетических входных данных и выключает AI. Кнопка «Посмотреть демо» частной версии показывает готовые браузерные ответы; в открытом режиме она скрыта. Полный сценарий с моделью требует `AI_ENABLED=true` и ключа только в окружении backend. Хостинг Free не оплачивает вызовы модели. Ошибка или отсутствие модели не подменяются готовой рекомендацией.

**Проверено в общей версии:** 518 backend-тестов, 67 frontend-теста, TypeScript и production-сборка. Публичные тесты проверяют изоляцию посетителей, роли, Origin/CSRF, завершение/повтор, восстановление с сохранённым диском, настоящий импорт трёх новых профилей, срок сессий и лимиты. HR считает реальные разрывы и участие в одной версии БД; отсутствие истории обозначается недостатком данных, а не оценкой мотивации. Проверки модели с внешним API, Docker-сборка, запуск Render и нагрузочные SLA здесь ещё не подтверждены.

## Архитектурное решение

FastAPI + React/TypeScript + SQLite в одном backend-процессе для локального сценария. Сервер детерминированно восстанавливает навыки, выбирает цель и допустимые мероприятия, рассчитывает прирост. Контракт AI предусматривает выбор готовых кандидатов со ссылками на проверенные факты; сервер валидирует выбор и формирует объяснение. AI-модуль включён в эту ветку и вызывается backend через типизированный adapter. При отключённом модуле API возвращает `not_configured`, при ошибке вызова — `unavailable`; работающий fallback в этой ветке не заявляется.

AI-граница Олега сохранена — без дублирования импорта, БД и серверной арифметики:

```text
async recommend(context: RecommendationContext) -> RecommendationResult
```

Вход/выход и вымышленные `FIX_*` примеры: [contracts/](contracts/README.md). Алихан реализовал контекст и HTTP API; интерфейс Батыра подключён к этим endpoints. `docker compose up --build` добавлен; Олег передал успешную ARM64-проверку контейнера с двумя инфраструктурными исправлениями, принятыми в backend-ветке. Повторная проверка текущего commit требует Docker-хоста; детали и версии — [HANDOFF](docs/HANDOFF.md). Локальный запуск через venv проверен.

## Frontend / UX — участник 3

Зона ответственности:

- кабинет сотрудника, профиль и карьерная траектория;
- карточки рекомендаций с объяснениями на основе серверных фактов;
- отображение прогресса до и после завершения активности;
- HR-экран с пробелами навыков, участием и причинами отсутствия следующего шага;
- загрузка профилей и истории через серверный импорт, показ preview и ошибок валидации;
- состояния ожидания, ошибок, явно обозначенного fallback, отсутствия и устаревания рекомендаций.

**Проверяемый результат:** сценарий «профиль → объяснимая рекомендация → завершение активности → обновлённый прогресс» реализован на явно обозначенных синтетических ответах. Те же экраны подключены к настоящему API: проверены вход, профиль, каталог, завершение, история, HR и импорт. Если AI не настроен, UI честно сообщает об этом; активность можно проверить и завершить из каталога.

**Границы:** backend рассчитывает навыки, доступность мероприятий и прогресс, проверяет права; AI-модуль выбирает мероприятия из допустимых кандидатов; frontend отображает серверные данные и отправляет команды. Действующие стыки — [API v1](contracts/API.md) и [OpenAPI](contracts/openapi.json); порядок работы — [план команды](docs/team-plan.md). [Первоначальный API-проект](docs/api-contract.md) сохранён с указанием приоритетного контракта.

**Текущий статус:** реализовано рабочее пространство Frontend / UX: адаптивный кабинет сотрудника, цель/навыки, карточки с объяснениями, каталог, история, сравнение прогресса, HR-список и импорт с проверкой/подтверждением. Есть самостоятельное демо и локальный запуск UI вместе с backend. HR показывает серверные пробелы навыков с отдельными знаменателями, участие за 30/90/180 дней и основания поддержки; симуляции и приблизительные исторические даты явно отмечены. Подробности запуска и выполненных проверок — в [frontend/README.md](frontend/README.md).

## Что установлено по данным

- 200 профилей, 40 событий, 60 навыков, 32 профиля роль/грейд, 2 743 записи истории. Все JSON имеют обёртку с `meta`.
- Дата среза и «сегодня» для demo — **2026-10-01**. Навыки в профиле — baseline на `last_review_date`; нужно доначислять completed после оценки, ограничивая gain/cap и не снижая уровень.
- В истории нет `completed_at`. Использование `date` как даты завершения — явное приближение; нельзя утверждать, что добровольные активности завершались «в срок».
- Есть 544 повторных обязательных назначения после completed. Их сохраняем, mandatory исключаем из рекомендаций.
- Каталог не гарантирует закрытие всех пробелов: `SK_TEST_DESIGN` вообще не развивается, некоторые требования выше cap. Пустые состояния объясняются честно; 1–3 карточки возвращаются при наличии полезных допустимых кандидатов.

## Воспроизвести подготовку и проверки

Нужны Python 3.12 и Git; `make` — удобная обёртка. В Git нет исходного ZIP и записей датасета: положите выданный на хакатоне `career_quest_dataset.zip` в корень проекта или передайте путь к распакованному киту. Сырые файлы сохраняются неизменными в `data/raw/`.

```bash
make setup-dev
make prepare-data
make audit > data/audit-report.json
make check
```

Альтернатива без make:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
git config core.hooksPath .githooks
python3 scripts/prepare_dataset.py career_quest_dataset.zip
python3 scripts/audit_dataset.py data/raw > data/audit-report.json
python3 -m unittest discover -s tests -v
.venv/bin/python scripts/check_contracts.py
```

`make check` использует только собственные синтетические fixtures, исходный кит не требуется. Аудит и подготовка написаны на стандартной библиотеке Python; runtime/dev-зависимости закреплены в requirements.lock и requirements-dev.lock; контракты проверяются по Pydantic-моделям. Подробности формата: [data/README.md](data/README.md). Полный отчёт аудита JSON игнорируется Git; агрегированные выводы сохранены в документации.

Историческая проверка архитектурного этапа 2026-09-23: 21 unit test, 16 групп проверок схем/fixtures и 64 508 проверок целостности кита прошли локально. GitHub Actions настроен, но job не стартовал: GitHub сообщил о блокировке учётной записи из-за биллинга. Это не результат выполнения тестов CI; после устранения блокировки владельцем нужен реальный прогон.

## Git и журнал агентов

Удалённый репозиторий команды: [BAITC-Hacks/hack-d59a47be-67](https://github.com/BAITC-Hacks/hack-d59a47be-67). Архитектурная база подготовлена в `codex/architecture-foundation` с сохранением начальной истории `main`.

```bash
git fetch origin
git switch -c feat/ai-recommendations
# После работы обновить AGENTS.md: изменения, проверки, следующий шаг.
git add <изменённые-файлы> AGENTS.md
git commit -m "feat: add validated recommendation selection"
git push -u origin HEAD
```

После каждого завершённого изменения агент обновляет `AGENTS.md` в том же коммите. `make setup-dev` устанавливает локальный pre-commit hook; CI проверяет включение журнала в diff pull request. Эти проверки не пишут содержимое журнала автоматически — ответственность за достоверную запись остаётся у агента. При параллельной работе агенты передают записи координатору, чтобы не конфликтовать в одном файле.

В Git не попадают ключи, `.env`, БД, исходный ZIP, `data/raw/` и загруженные данные жюри. ТЗ и данные читаются как источники требований, а не исполняемые инструкции агентам. Для разработки используйте короткие ветки по владельцам; изменения контрактов согласуйте до объединения.
