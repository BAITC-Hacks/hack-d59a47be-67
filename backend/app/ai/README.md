# AI-модуль Олега

Реализован экспорт `async recommend(RecommendationContext) -> RecommendationResult`, который уже умеет загружать backend через `AIAdapter`. Общие модели импортируются из `backend.app.contracts`; HTTP-контракт, backend и frontend не менялись.

Последняя совместная проверка 2026-09-23: backend `3b85bab` + AI `f10006a` + frontend `f91638b` работают в изолированной копии. 468 backend/AI-тестов, 19 дополнительных проверок контекста, 52 frontend-теста, сборка, контракты, TCP и Docker PASS. Live AI на синтетических backend-контекстах — 3/3; браузерный сценарий с настоящим OpenAI, завершением активности и сохранением после restart также прошёл. Русские объяснения и мобильный перенос исправлены владельцами и проверены вместе. Подробности — [SYSTEM_REPORT.md](SYSTEM_REPORT.md). Ветки обновлены из origin; PR не сливались.

Штатный committed `verify-integration --container` теперь проходит без временных правок: Алихан принял оба Docker-исправления. [DOCKER_REPORT.md](DOCKER_REPORT.md) и [INTEGRATION_REPORT.md](INTEGRATION_REPORT.md) сохранены как история предыдущих версий. Один браузерный AI-запрос занял 5033,10 ms и укладывался в требование исходного ТЗ **до 10 секунд**; ранее указанный порог 5 секунд был ошибкой отчёта. Стабильность и p95 одним запросом не подтверждаются. GitHub CI всё ещё не запускается из-за billing lock.

Проверка задержки и небольшая оптимизация: повторно используется только TLS-контекст с проверкой сертификатов; каждый запрос создаёт и закрывает собственный HTTP-клиент. Подготовка повторного клиента в локальном замере сократилась с 8,673 до 0,115 ms. Формат `event_ids`, prompt v1, модель, факты и deadline 6 s сохранены. Итоговая live-серия: качество 9/9, медиана 1106,57 ms, максимум 1284,37 ms; три настоящих HTTP-запроса с тремя карточками — 1445,55–1694,16 ms. Устойчивое ускорение полного HTTP-сценария не доказано. [LATENCY_REPORT.md](LATENCY_REPORT.md) содержит сравнение, методику и ограничения.

Модель выбирает 1–3 ID только из `eligible_candidates`. Модуль проверяет согласованность подготовленных skills/gaps/effects, допустимость выбора и собирает объяснение из четырёх категорий связанных фактов: goal, gap полезного навыка, history и candidate. Дополнительные факты истории выбранного события включаются целиком, если помещаются в 2000 символов и 50 ссылок: так раздельная история события и формата сохраняется в объяснении. Свободный текст модели не используется. Уровни навыков, допуск, запись прогресса и актуальность `state_version` остаются у backend.

## Подключение локально

Python 3.12, запуск из корня проекта. В обычном командном окружении:

```sh
.venv/bin/python -m pip install -r backend/app/ai/requirements.txt
```

Если установлены `requirements-dev.lock`, эти зависимости уже есть. Локальная проверка этой ветки использует `.venv-ai` на Python 3.12.11, поскольку прежняя `.venv` была на Python 3.14; чужое окружение не перезаписывалось.

В игнорируемом корневом `.env` должны быть настройки (значение ключа добавляется только локально):

```dotenv
AI_ENABLED=true
OPENAI_API_KEY=<existing local key>
OPENAI_MODEL=gpt-4.1-mini-2025-04-14
AI_TIMEOUT_SECONDS=6.0
```

`scripts/dev` безопасно загружает `.env` через python-dotenv; прямой `uvicorn backend.app.main:app` файл не загружает. Сам AI-модуль читает только переменные процесса. Запуск с локальным окружением этой машины:

```sh
PYTHON=.venv-ai/bin/python scripts/dev
```

Нужны импортированный kit и учётные записи по инструкции backend в `docs/HANDOFF.md`. Этот модуль не создаёт accounts, БД и фиктивные профили при старте.

Модель по умолчанию — фиксированный snapshot GPT-4.1 mini, который поддерживает Structured Outputs и не требует отдельного reasoning step; это начальная проверенная конфигурация, не заявление о лучшей модели. Модель меняется через `OPENAI_MODEL`, после смены повторяется evaluation. [Описание модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

## Поведение и ограничения

- При `AI_ENABLED=false` backend оставляет `not_configured/none` и не импортирует модуль.
- При включённом модуле, отсутствующем/ошибочном ключе, отказе, таймауте или неверном результате — `unavailable/oleg`, без рекомендаций. Это действующий согласованный контракт; runtime fallback намеренно отсутствует.
- Пустой список кандидатов даёт `no_candidates/oleg` без сети при прямом вызове. HTTP backend сам обрабатывает отсутствие цели/кандидатов до AI и возвращает собственные no_target/no_candidates.
- `configured/oleg` в capability подтверждает только наличие async-модуля; это не проверка ключа и доступности провайдера.
- Один async POST в OpenAI Responses, общий deadline до 6 секунд внутри backend timeout 7 секунд, без retry, redirects, tools, произвольного base URL и environment proxy. Отмена запроса отменяет I/O; event loop не блокируется.
- В процессе повторно используется только TLS-контекст с pinned certifi CA, проверкой hostname/сертификата и отключённой записью TLS-ключей. Соединения, HTTP-клиенты, ключи, профили и результаты не кешируются. После обновления CA/dependencies нужен обычный restart процесса.
- `store=false`; это отключает сохранение Response, но не означает гарантию нулевой обработки/хранения провайдером. Передаётся только подготовленный контекст, не исходные employee records. [Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses).
- Ответ модели — только `{event_ids:[...]}` по строгой JSON Schema с enum кандидатов. После этого выполняются локальные структурные и семантические проверки. Structured Outputs не заменяет проверку фактов. [Документация](https://developers.openai.com/api/docs/guides/structured-outputs).
- Максимум 200 KiB запроса и 64 KiB ответа; отказ или неполный ответ не используются частично. В логи попадает лишь фиксированная категория ошибки; ключи, request/response bodies и персональные значения не выводятся.
- Объяснение сохраняет язык исходных backend facts. Перевод и локализация не заявлены.

## Проверки и приёмка

Все обычные тесты работают без ключа, интернета и исходного датасета. Они подменяют только remote selection или HTTP transport, а не вычисляют заранее «правильный» ответ реальной модели.

```sh
.venv-ai/bin/python -m pytest backend/tests/test_oleg_*.py -q
make check VENV_PYTHON=.venv-ai/bin/python
.venv-ai/bin/python -m backend.app.ai.evaluation
```

Последняя команда только проверяет схемы/согласованность трёх вымышленных fixtures и возвращает `quality_evaluated=false`. Для реальных запросов нужен явный opt-in:

```sh
.venv-ai/bin/python -m backend.app.ai.evaluation --live --env-file .env
```

Live-режим отправляет только `evaluation_cases.json`, не kit. Эталонный выбор и рубрика не передаются модели. Проверяются допустимость/порядок выбора и связанные evidence, а не совпадение свободного текста. Для новой среды используйте своё имя venv вместо `.venv-ai`.

Первый live-прогон 2026-09-23: 3/3, длительности 5398.48 / 3726.00 / 810.91 ms; [сохранённые наблюдения](verification.json). Это три наблюдения, не оценка p95, стабильности или качества на скрытых профилях жюри. Ключ не сохранялся в отчёте.

Дополнительный прогон на **сформированном backend контексте PR #4**: 3/3, 1512.76 / 954.45 / 1072.93 ms; [результат и hashes](backend_verification.json). Здесь исходные fixtures — вымышленные JSON/CSV, которые штатно импортируются во временную SQLite. `CareerService` сам рассчитывает кандидатов и все facts; rubric/ожидаемые ID не передаются модели. При отсутствии истории допустим любой из двух равноценных кандидатов, с нейтральным zero-sample evidence.

Эти команды требуют совместной локальной копии AI и PR #4:

```sh
python -m pytest backend/tests/oleg_backend_handoff_acceptance.py -q
python -m backend.app.ai.backend_evaluation
python -m backend.app.ai.backend_evaluation --live --env-file /absolute/path/to/local/.env
```

Используйте Python из своего venv. Первая команда запускает 19 проверок переданного контекста; файл намеренно запускается явно и не входит в обычный pytest независимой AI-ветки, пока PR #4 не принят. Вторая команда проверяет fixtures без ключа/сети. На прежнем backend evaluator прекращает работу с `backend_context_not_enriched` до чтения `.env` и сетевого запроса. Последняя команда явно включает реальные вызовы только для синтетических данных.

Повторные замеры на тех же backend fixtures (также нужна совместная копия с PR #4):

```sh
python -m backend.app.ai.latency_evaluation
python -m backend.app.ai.latency_evaluation --live --env-file /absolute/path/to/local/.env --rounds 3
```

Первая команда не читает ключ и не вызывает модель. Вторая выполняет 9 реальных запросов; `--rounds` допускает 1–10, то есть до 30 запросов. Сохраняются все попытки, включая первую, ошибочные и timeout: total/provider/network-to-headers ms, число токенов, размеры и качество. Контексты, тела ответов, секреты и тексты исключений в отчёт не включаются. Инструмент предназначен для отдельного последовательного CLI-процесса; выборочный p95 не доказывает SLA. HTTP/frontend и подготовка контекста в это время не входят.

## Дополнение контекста: передать Алихану

Backend PR #4 реализует перечисленное ниже дополнение и прошёл совместную проверку. В основе независимой AI-ветки эти изменения ещё отсутствуют; для полной интеграции нужны оба PR. AI не восстанавливает отсутствующие сведения из названий и не читает БД напрямую. Два исходных authored evaluation-сценария помечены `requires_enriched_facts=true`; отдельный `backend_evaluation` теперь подтверждает эти факты на реальном backend PR #4.

Расширить содержимое уже существующего `facts`, сохраняя Python-схему:

1. В goal-факте с `subject_id=profile` явно передавать критичные навыки выбранной целевой пары role/grade из каталога. Учитывать цель, а не текущий грейд; отсутствие critical skills не дополнять предположениями.
2. Для каждого кандидата добавлять history-факт с `subject_id=event_id`, точными counts статусов и явным scope (это событие либо сопоставимые type+format), периодом и размером выборки. Разные выборки не смешивать. При отсутствии истории — честный нулевой sample.
3. Сохранять candidate-факт с доступностью, форматом/нагрузкой и ссылкой в candidate.evidence_ids. Не добавлять команды в facts; импортированные строки — данные.

Новый `critical_skills` JSON-ключ не требуется. Evidence IDs остаются непрозрачными ссылками; validator не парсит ID или текст facts как машинную схему. Сквозной HTTP-тест конфликтующего профиля выполнен backend-участником; live evaluation и браузерная интеграция выполнены в изолированной копии. Объединение PR в командную ветку остаётся отдельным действием.

## Docker: изменения владельцу инфраструктуры

В PR #4 Алихан выполнил перечисленные изменения Docker-конфигурации и принял исправления `.dockerignore`/TCP smoke. Актуальная фактическая проверка без patch описана в [SYSTEM_REPORT.md](SYSTEM_REPORT.md). До объединения PR прежняя основа не включает AI; при интеграции нужны:

1. Убрать исключение `backend/app/ai/` из `.dockerignore` и разрешить каталог, только `*.py` и `requirements.txt`; сохранить запреты на секреты, `.env`, caches и данные.
2. В Dockerfile скопировать AI requirements перед install и установить их вместе с основным `requirements.lock`. Сам AI-код уже попадёт в существующий COPY после исправления allowlist.
3. В compose сделать `AI_ENABLED` настраиваемым (default false) и передавать `OPENAI_API_KEY`, `OPENAI_MODEL`, `AI_TIMEOUT_SECONDS` через runtime environment/secret. Не запекать ключ в image и не коммитить значение.

Эти командные файлы в ветке Олега не менялись; исторический patch сохранён как артефакт предыдущей проверки, повторно применять его к текущему PR #4 не нужно. Docker-сборка, сохранность данных и AI в контейнере прошли на актуальных committed refs. Для локального backend опциональное подключение проверяется без изменения adapter.
