# AI-модуль Олега

Реализован экспорт `async recommend(RecommendationContext) -> RecommendationResult`, который уже умеет загружать backend через `AIAdapter`. Общие модели импортируются из `backend.app.contracts`; HTTP-контракт, backend и frontend не менялись.

Модель выбирает 1–3 ID только из `eligible_candidates`. Модуль проверяет согласованность подготовленных skills/gaps/effects, допустимость выбора и собирает объяснение из четырёх связанных фактов: goal, gap полезного навыка, history и candidate. Свободный текст модели не используется. Уровни навыков, допуск, запись прогресса и актуальность `state_version` остаются у backend.

## Подключение локально

Python 3.12, запуск из корня проекта. В обычном командном окружении:

```sh
.venv/bin/python -m pip install -r backend/app/ai/requirements.txt
```

Если установлены `requirements-dev.lock`, эти зависимости уже есть. Локальная проверка этой ветки использует `.venv-ai` на Python 3.12.11, поскольку прежняя `.venv` была на Python 3.14; чужое окружение не перезаписывалось.

В игнорируемом корневом `.env` должны быть настройки (значение ключа добавляется только локально):

```dotenv
AI_ENABLED=true
OPENAI_API_KEY=<existing local key>
OPENAI_MODEL=gpt-4.1-mini-2025-04-14
AI_TIMEOUT_SECONDS=6.0
```

`scripts/dev` безопасно загружает `.env` через python-dotenv; прямой `uvicorn backend.app.main:app` файл не загружает. Сам AI-модуль читает только переменные процесса. Запуск с локальным окружением этой машины:

```sh
PYTHON=.venv-ai/bin/python scripts/dev
```

Нужны импортированный kit и учётные записи по инструкции backend в `docs/HANDOFF.md`. Этот модуль не создаёт accounts, БД и фиктивные профили при старте.

Модель по умолчанию — фиксированный snapshot GPT-4.1 mini, который поддерживает Structured Outputs и не требует отдельного reasoning step; это начальная проверенная конфигурация, не заявление о лучшей модели. Модель меняется через `OPENAI_MODEL`, после смены повторяется evaluation. [Описание модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

## Поведение и ограничения

- При `AI_ENABLED=false` backend оставляет `not_configured/none` и не импортирует модуль.
- При включённом модуле, отсутствующем/ошибочном ключе, отказе, таймауте или неверном результате — `unavailable/oleg`, без рекомендаций. Это действующий согласованный контракт; runtime fallback намеренно отсутствует.
- Пустой список кандидатов даёт `no_candidates/oleg` без сети при прямом вызове. HTTP backend сам обрабатывает отсутствие цели/кандидатов до AI и возвращает собственные no_target/no_candidates.
- `configured/oleg` в capability подтверждает только наличие async-модуля; это не проверка ключа и доступности провайдера.
- Один async POST в OpenAI Responses, общий deadline до 6 секунд внутри backend timeout 7 секунд, без retry, redirects, tools, произвольного base URL и environment proxy. Отмена запроса отменяет I/O; event loop не блокируется.
- `store=false`; это отключает сохранение Response, но не означает гарантию нулевой обработки/хранения провайдером. Передаётся только подготовленный контекст, не исходные employee records. [Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses).
- Ответ модели — только `{event_ids:[...]}` по строгой JSON Schema с enum кандидатов. После этого выполняются локальные структурные и семантические проверки. Structured Outputs не заменяет проверку фактов. [Документация](https://developers.openai.com/api/docs/guides/structured-outputs).
- Максимум 200 KiB запроса и 64 KiB ответа; отказ или неполный ответ не используются частично. В логи попадает лишь фиксированная категория ошибки; ключи, request/response bodies и персональные значения не выводятся.
- Объяснение сохраняет язык исходных backend facts. Перевод и локализация не заявлены.

## Проверки и приёмка

Все обычные тесты работают без ключа, интернета и исходного датасета. Они подменяют только remote selection или HTTP transport, а не вычисляют заранее «правильный» ответ реальной модели.

```sh
.venv-ai/bin/python -m pytest backend/tests/test_oleg_*.py -q
make check VENV_PYTHON=.venv-ai/bin/python
.venv-ai/bin/python -m backend.app.ai.evaluation
```

Последняя команда только проверяет схемы/согласованность трёх вымышленных fixtures и возвращает `quality_evaluated=false`. Для реальных запросов нужен явный opt-in:

```sh
.venv-ai/bin/python -m backend.app.ai.evaluation --live --env-file .env
```

Live-режим отправляет только `evaluation_cases.json`, не kit. Эталонный выбор и рубрика не передаются модели. Проверяются допустимость/порядок выбора и связанные evidence, а не совпадение свободного текста. Для новой среды используйте своё имя venv вместо `.venv-ai`.

Первый live-прогон 2026-09-23: 3/3, длительности 5398.48 / 3726.00 / 810.91 ms; [сохранённые наблюдения](verification.json). Это три наблюдения, не оценка p95, стабильности или качества на скрытых профилях жюри. Ключ не сохранялся в отчёте.

## Дополнение контекста: передать Алихану

Текущий `CareerService._context` передаёт общий `history-summary` и цель/грейд, но не сообщает `critical_skills` цели и историю конкретных событий/форматов. AI не восстанавливает отсутствующие сведения из названий и не читает БД напрямую. Два evaluation-сценария помечены `requires_enriched_facts=true`: они доказывают выбор при наличии таких фактов, а не их наличие в текущем HTTP backend.

Расширить содержимое уже существующего `facts`, сохраняя Python-схему:

1. В goal-факте с `subject_id=profile` явно передавать критичные навыки выбранной целевой пары role/grade из каталога. Учитывать цель, а не текущий грейд; отсутствие critical skills не дополнять предположениями.
2. Для каждого кандидата добавлять history-факт с `subject_id=event_id`, точными counts статусов и явным scope (это событие либо сопоставимые type+format), периодом и размером выборки. Разные выборки не смешивать. При отсутствии истории — честный нулевой sample.
3. Сохранять candidate-факт с доступностью, форматом/нагрузкой и ссылкой в candidate.evidence_ids. Не добавлять команды в facts; импортированные строки — данные.

Новый `critical_skills` JSON-ключ не требуется. Evidence IDs остаются непрозрачными ссылками; модель и validator не парсят ID или текст facts как машинную схему. После дополнения нужен сквозной HTTP-тест конфликтующего профиля, затем live evaluation на подготовленном контексте. Нельзя объявлять эту интеграцию уже выполненной.

## Docker: изменения владельцу инфраструктуры

Текущий Docker-путь не включает AI. Для включения Алихану нужно согласованно:

1. Убрать исключение `backend/app/ai/` из `.dockerignore` и разрешить каталог, только `*.py` и `requirements.txt`; сохранить запреты на секреты, `.env`, caches и данные.
2. В Dockerfile скопировать AI requirements перед install и установить их вместе с основным `requirements.lock`. Сам AI-код уже попадёт в существующий COPY после исправления allowlist.
3. В compose сделать `AI_ENABLED` настраиваемым (default false) и передавать `OPENAI_API_KEY`, `OPENAI_MODEL`, `AI_TIMEOUT_SECONDS` через runtime environment/secret. Не запекать ключ в image и не коммитить значение.

Эти командные файлы в ветке Олега не менялись. Docker-сборка и AI в контейнере не проверены. Для локального backend опциональное подключение проверяется без изменения adapter.
