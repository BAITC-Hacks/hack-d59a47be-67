# Docker и единый демо-сценарий — 2026-09-23

Контейнерная приёмка и сценарий frontend → Docker backend → живой OpenAI прошли **после двух правок во временной копии**. Исходный `scripts/verify-integration --ai-ref origin/codex/ai-recommendations --container` на проверенных коммитах завершился ошибкой; считать его зелёным до принятия исправлений нельзя. Готовый [patch для Алихана](verification/container-fixes.patch) меняет только `.dockerignore` и `scripts/smoke.py`. В командных ветках эти файлы не редактировались, PR не сливались, публичного деплоя не было.

## Два обнаруженных блокера

1. **TCP smoke ожидает ровно четыре evidence IDs.** AI теперь сохраняет и историю события, и историю похожего формата, поэтому корректных ссылок пять. 442 backend/AI теста, 21 исходный тест, 9 schema checks и Ruff прошли, затем `scripts/smoke.py` остановился на `len(...) == 4`, до запуска Docker.
2. **`.dockerignore` повторно включает весь AI-каталог.** Прямой `scripts/check_container.py --require-ai` собрал исходный образ, но завершился `Image contains a forbidden file`: внутри обнаружены AI README, JSON-fixtures/отчёты и screenshots. UID=10001, `/data` пустой, ключ в образе отсутствовал. Утечка ключа или рабочей базы не обнаружена.

Patch возвращает исключение `backend/app/ai/**` перед разрешением `*.py` и `requirements.txt`. В smoke вместо жёсткого количества проверяются уникальность/лимит ссылок, категории и принадлежность фактов цели/навыку/событию, обе истории этой небольшой fixture и точное совпадение текста с доверенными facts. Не вводится парсинг префиксов IDs. Patch применяется чисто; Ruff/syntax PASS, актуальный результат с пятью ссылками проходит, 12 повреждённых вариантов evidence/text отклонены.

## Что фактически прошло с patch

- `scripts/smoke.py --ai`: TCP-вызов настоящего AI-модуля с подменённым только удалённым selector, карточки/основания/latest, права, CSRF, повтор завершения и сохранение после restart — PASS. Сеть OpenAI в этом smoke не используется.
- `scripts/check_container.py --require-ai`: build, non-root, точный состав образа, пустая база, отсутствие ключа, импорт AI — PASS.
- Два цикла контейнера: health/readiness/version, login/права/CSRF, SQLite foreign_keys/busy_timeout/миграции — PASS.
- Пересоздание контейнера с тем же named volume: данные, сессия и точный результат повторного запроса завершения сохранились; повтор не начислил прогресс заново — PASS.

Это native ARM64-проверка. AMD64 и production не проверялись. Полная исходная команда не перезапускалась с фиктивными Git-коммитами: её этапы TCP/container выполнены на экспортированном дереве с явно указанным patch. До принятия patch исходный committed runner продолжит падать.

## Frontend с контейнерным API

Frontend запущен через Vite proxy на `127.0.0.1:5179`; API опубликован только на loopback, origin явно разрешён. База содержит отдельные синтетические профили frontend seed. Проверены:

1. Вход через обычную форму и загрузка профиля.
2. Реальный OpenAI через контейнерный HTTP endpoint: `ok/oleg`, три карточки с пятью evidence IDs, 1202 ms по browser performance.
3. Предпросмотр и подтверждение завершения **вымышленной** активности в изолированной тестовой базе, обычный `mode=completion`: навык 2→3, прогресс 56.25→62.5%, revision 1→2, отдельная completed-запись истории.
4. Старые рекомендации стали stale; UI блокирует действия по ним.
5. После `docker restart`, перезагрузки страницы и обновления proxy на назначенный Docker временный порт сохранились сессия, навык3, прогресс62.5%, три записи истории и три stale-карточки.

[Скриншот после рестарта](verification/docker-after-restart.png). При restart Docker изменил случайный опубликованный порт, поэтому proxy пришлось перенаправить. Для общей локальной демо-среды нужен стабильный loopback-порт; штатный Compose уже задаёт `127.0.0.1:8000:8000`.

Ранее выявленные UX-проблемы — технические английские facts в объяснениях и перенос текста на телефоне — этим Docker-прогоном не исправлялись; они описаны в [INTEGRATION_REPORT.md](INTEGRATION_REPORT.md).
