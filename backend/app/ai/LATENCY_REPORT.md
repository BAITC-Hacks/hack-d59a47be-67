# Задержка AI: проверка и изменение — 2026-09-23

Итоговая версия сохраняет качество синтетических рекомендаций 9/9 и укладывается в допустимые 10 секунд во всех зафиксированных запросах. Повторно используется только TLS-конфигурация с проверкой сертификатов: локальная подготовка повторного HTTP-клиента стала дешевле примерно на 8,6 ms. Существенное ускорение всего сетевого сценария не доказано; нет оснований обещать SLA по малой выборке.

## Исправление требования

Исходное ТЗ задаёт **UI до 2 секунд, AI до 10 секунд**: [RU, строка 54](../../../docs/requirements/original-spec.txt#L54), KZ строка 164, EN строка 277. AI-контракт сохраняет внешний timeout адаптера 7 s; внутренний AI deadline — 6 s. В прежнем SYSTEM_REPORT ошибочно использовался порог 5 s. Наблюдение 5033,10 ms не нарушало ТЗ. README, SYSTEM_REPORT и его JSON исправлены; сами измерения сохранены.

## Что изменено

`provider.py` лениво создаёт и повторно использует один `ssl.SSLContext` с тем же pinned certifi CA, который выбирает HTTPX при `trust_env=False`. Проверка hostname и сертификата обязательна, TLS key logging выключен. HTTP-клиент и соединение по-прежнему создаются и закрываются для каждого вызова; API-ключ, payload, ответ и профиль не кешируются. Ошибки загрузки сертификатов остаются обезличенными. После обновления CA/dependencies процесс перезапускается.

Новый `latency_evaluation.py` выполняет только фиксированные синтетические сценарии через настоящий backend-контекст. Default — offline; `--live` включает сеть, 1–10 раундов по 3 запроса. Порядок кейсов ротируется, первая попытка и ошибки не исключаются. Временные обёртки профилирования действуют только внутри отдельного последовательного CLI, не меняют production API и не сохраняют тела/заголовки/исключения.

Модель, prompt, wire `event_ids`, правила выбора, семантическая проверка и deadline не изменились. Backend, frontend, общие контракты и инфраструктурные исходники не редактировались.

## Измерения

| Вариант | Качество | Медиана AI entry point | Максимум / выборочный p95 | Выходных токенов на кейс |
|---|---|---|---|---|
| Baseline | 9/9 | 1159,96 ms | 1375,16 ms | 13 |
| Итоговый TLS reuse | 9/9 | 1106,57 ms | 1284,37 ms | 13 |

Ошибок и timeout в этих сериях не было. Выборочный p95 при n=9 методом nearest-rank совпадает с максимумом и не оценивает production p95. Изменение медианы примерно на 53 ms нельзя целиком приписать TLS-оптимизации.

Локальный замер без сети: по 20 созданий/закрытий клиента. Медиана повторных вызовов с отдельной загрузкой CA — **8,673 ms**, с общим проверенным TLS-контекстом — **0,115 ms**. Первые вызовы сохранены отдельно (65,869 и 7,907 ms) и не интерпретируются как честное сравнение холодного старта: зависимости/файловый кеш уже могли быть прогреты. Это оптимизация локальной подготовки, не TLS handshake или генерации модели.

Отдельно на baseline: создание трёх синтетических баз и контекстов — 12,771 ms суммарно; чистый engine с мгновенным тестовым selector, 100 повторов/кейс — медианы 0,119/0,107/0,109 ms. Поэтому валидация фактов не сокращалась ради скорости. В live baseline медиана provider — 1159,55 ms при общей 1159,96 ms: основное время находится внутри сетевого вызова.

## Настоящий HTTP-сценарий

Временная synthetic SQLite из frontend fixture, обычный HTTP login, настоящий backend с включённым AI; 3 POST рекомендации limit=3 на версию. Каждый ответ дал `ok/oleg`, три разных допустимых ID и русские объяснения с evidence. После последнего ответа прошли preview/completion; прогресс вырос 56,25% → 62,5%, latest стал stale.

| Вариант | HTTP запросы рекомендаций | Медиана |
|---|---|---|
| Baseline | 1200,42 / 1506,47 / 1158,62 ms | 1200,42 ms |
| Итоговый TLS reuse | 1445,55 / 1564,38 / 1694,16 ms | 1564,38 ms |

Полный HTTP-сценарий в итоговой серии оказался медленнее baseline, хотя оба варианта с запасом уложились в 10 s. **Ускорение end-to-end не заявляется.** Измерение GET профиля итогового запуска — 2,18 ms; это HTTP API, не измерение отрисовки UI. Браузер и frontend этой правкой не менялись; предыдущая браузерная приёмка остаётся в SYSTEM_REPORT.

Предварительный HTTP-прогон остановился на неверном payload preview в проверочном скрипте (использованы `event_id` вместо `event_ids` и пропущена версия). Три выполненных AI-вызова этого прогона не имеют сохранённых timings и не включены в таблицу; после исправления скрипта baseline повторён целиком. Это ошибка QA-скрипта, не приложения.

## Проверенный, но не принятый вариант

Пробовали возвращать из модели короткие индексы кандидатов и преобразовывать их в исходные ID. Качество — 9/9, выходных токенов 13 → 7; медиана AI 1106,89 ms, максимум 1915,18 ms, медиана HTTP с тремя карточками 1599,47 ms. Польза для полного времени не доказана, поэтому изменение wire/prompt **не включено** в итоговый код. Это соответствует подходу «измерить и проверить качество»; общее правило сокращения вывода из [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization) не заменяет измерение конкретного приложения.

Все варианты, включая отвергнутый, сохранены в JSON для проверки вывода.

Этот прогон использовал экспорт backend commit + перечисленные hash итоговых AI-файлов, а не заранее существующий AI commit. Live-проверки выше выполнены на Mac через настоящий сетевой OpenAI; container checker использует synthetic selector и не подменяет этот факт.

Серверы HTTP, временные synthetic DB/credentials и Docker-projects остановлены/очищены адресно. Чужие исходники, данные, `.env` и ресурсы не менялись. Никаких публичных deploy или merge PR. Известная billing lock GitHub CI остаётся задачей владельца аккаунта.
