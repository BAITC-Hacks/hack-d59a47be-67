# Точечное расширение v1 — согласовано

Владелец задачи явно согласовал изменения с потребителями 2026-09-23: «Согласовано через меня — реализовать». Python-интерфейс Олега `RecommendationContext -> RecommendationResult` сохраняется без изменений. Единый источник схем — `backend/app/contracts.py`.

Причина: исходные planned-схемы не представляли неполную импортную историю, совместный импорт, происхождение дат и сохранённые устаревшие рекомендации. Согласованы следующие точечные изменения.

1. Сохранить `state_version` / `expected_state_version`; считать их общей монотонной revision набора демо. Любая запись цели, завершения или импорта увеличивает revision, все старые рекомендации становятся stale. `data_version` отражает версию кита и revision. Это консервативная инвалидация для одного процесса.
2. Дополнить профиль `scenario_date`, `target_status=explicit|next_grade|no_target` и backend-рассчитанным `progress`. `goal` остаётся nullable. История получает `record_id`, `status`, `activity_date`, `date_source=historical_proxy|completed_at`, nullable `completed_at`, `mode=import|completion|demo_simulation`, эффекты. Существующий `CompletionRecord` для новых действий сохраняется.
3. HTTP `RecommendationResponse` дополнить `recommendation_id`, `stale` и статусом `no_target`; `no_candidates`/`no_target` могут вычисляться backend с `engine=none`. Контракт Олега `RecommendationContext -> RecommendationResult` не менять. Добавить `GET /api/employees/{id}/recommendations/latest`: полные сохранённые карточки и explanations, `stale=true` после изменения revision; 404, если результата ещё нет.
4. `POST .../completions` требует `Idempotency-Key`. Старое тело сохраняется; добавить необязательный `record_id`, чтобы завершать конкретное назначение, включая повторные mandatory. Новые действия имеют серверный timezone-aware `completed_at`; исторический `date` остаётся приблизительным, без подмены его точным временем. Повтор ключа/тела проверяется после прав и до revision.
5. Сохранить одиночный `ImportRequest`. Дополнительно принимать batch `{dry_run, files:[{source_filename,source_format,content}], preview_token?}` в том же `POST /api/hr/import`. Файлы — существующие реальные JSON-обёртки/CSV, без новых полей внутри них. `dry_run=true` возвращает validation/preview token, revision и счётчики; commit требует этот token и тот же набор файлов. Новый профиль и его история проходят проверку в одной партии; commit атомарен. Одиночному запросу также добавить `preview_token?`. Изменённые существующие record_id конфликтуют; разные record_id никогда не удаляются по совпадению employee/event/date.
6. Дополнить каталог событиями для рабочего frontend preview/completion. Старые поля каталога сохраняются; availability/effects — authoritative backend, а не frontend.

`Progress` содержит `percent` (0–100), `met_skills`, `total_skills`, `critical_met`, `critical_total`. `ImportResponse` дополнен `preview_token`, `revision`, `counts`; `imported_records` сохранён. История использует все шесть исходных статусов: `completed`, `in_progress`, `dropped`, `no_show`, `declined`, `overdue`.

Серверный `completed_at` нового действия использует demo-часы: дату `as_of_date` из метаданных и текущее UTC-время суток. Реальное время принятия записи отдельно хранится для аудита как `recorded_at`; оно не выдаётся за дату исторического завершения. API явно помечает `date_source`. Изменения в `frontend/` и `backend/app/ai/` не требуются.
