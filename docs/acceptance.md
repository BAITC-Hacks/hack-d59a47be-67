# Приёмка Career Quest

Статус: план проверки будущей реализации. Перечисленные сценарии ещё не выполнены. Источники: [исходное ТЗ](requirements/original-spec.txt), README.ru.md локального стартового кита и [архитектура](architecture.md). Оценивается только кейс Career Quest.

## Соответствие обязательным требованиям

| ID | Требование ТЗ | Ответственный модуль | Проверка и ожидаемый результат |
|---|---|---|---|
| A01 | Профиль и карьерная траектория | Backend: profiles, skills; Frontend: профиль | Открыть произвольного разрешённого сотрудника: роль, грейд, текущие навыки, история, требования следующего грейда, разрывы и доступные шаги согласованы с API. Для Lead явно показать отсутствие следующего грейда. |
| A02 | 1–3 релевантные AI-рекомендации | Backend: eligibility; AI: recommendations | При `planning_state=actionable` получены 1–3 уникальных допустимых `event_id`; количество не превышает число кандидатов. Выбор использует профиль, целевые требования и историю. Пустой ответ содержит нормативную причину из L08. |
| A03 | Объяснение минимум по трём факторам | AI: evidence, validator; Frontend: карточка | Объяснение каждой рекомендации опирается минимум на три разных фактора из грейда, разрыва навыков, истории и требований следующего уровня. Числа и ссылки подтверждаются серверными фактами; три перефразирования одного разрыва не считаются тремя факторами. |
| A04 | Изменение прогресса после выполнения | Backend: activity, skills, transaction; Frontend: прогресс | Завершить подходящую активность: одна запись результата, корректные приращения, новый профиль и траектория. Повтор запроса не начисляет рост второй раз. Уровень не понижается. |
| A05 | Простой HR-view | Backend: HR aggregates, auth; Frontend: HR | Видны частота разрывов по навыкам, сотрудники без рекомендованного шага и участие по активностям. Результат сверяется с ручным расчётом на маленьком fixture; знаменатели и дата среза подписаны. |
| A06 | Загрузка проверочных профилей и истории | Backend: import; Frontend: загрузка | Войти как HR, загрузить JSON сотрудников в обёртке `{meta, employees: [...]}` и CSV истории в формате кита, проверить отчёт и подтвердить атомарное сохранение. Новые профили сразу доступны для A01–A05 без изменения кода. |
| A07 | Приватность и employee/HR | Backend: auth, все API | Сотрудник получает только свой профиль и свою историю; прямой запрос к чужому ID, HR-агрегатам и импорту отклоняется сервером. HR получает разрешённый срез. Скрытие кнопки не является проверкой прав. |
| A08 | Задержки | Backend, AI, Frontend | На заявленном оборудовании отклик интерфейса и обычного API не более 2 с, получение AI-рекомендации не более 10 с. Отдельно измерить обычный успех, холодный вызов и таймаут; записать условия и результаты. Ожидание AI не блокирует профиль. |
| A09 | Репозиторий, README, запуск одной командой | Backend: запуск; владелец: README/приёмка | Проверяющий из чистой копии выполняет инструкции, локально добавляет разрешённый кит и запускает приложение одной командой. README описывает переменные окружения, demo-учётные записи, AI/fallback и ограничения. |
| A10 | Ограничения продукта | Все участники | Нет публичного рейтинга сотрудников, механик награждения за обязательные процессы и реальных персональных данных. Обязательные события видны в истории, но не выдаются как добровольные рекомендации. |

## Детерминированная логика и данные

Дата бизнес-среза для исходного кита — `2026-10-01`, независимо от даты компьютера. Это правило README датасета. Все fixtures ниже синтетические; записи исходного кита в Git не добавляются.

| ID | Сценарий | Ожидаемая проверка |
|---|---|---|
| D01 | Базовый навык и replay | База берётся из `employees.skills` на `last_review_date`. Учитываются только `completed` после этой даты и не позднее даты среза; `in_progress`, `dropped`, `no_show`, `declined`, `overdue` не дают роста. История до оценки остаётся доступной для объяснения участия. |
| D02 | Граница даты оценки | Завершения до, в день и после `last_review_date`: только последнее входит в replay. Одинаковый ввод повторно даёт тот же результат. |
| D03 | Ограничение роста | Для текущего уровня `s`: `max(s, min(5, s + gain, max_level))`. Проверить ниже лимита, на лимите и выше лимита события, а также отсутствующий навык (`0`). Например, `s=4`, `gain=1`, `max_level=3` оставляет `4`. |
| D04 | Неоднозначная дата истории | В ките нет `completed_at`: `date` для self-paced означает зачисление, для остальных — сессию. Принятое допущение replay использует `date` как proxy времени завершения и явно документируется. Среди 318 completed после оценки 139 относятся к self-paced. Эти даты не доказывают завершение в срок. Новые завершения хранят собственное фактическое время; тест не выдаёт proxy за точный факт. |
| D05 | Допустимость события | Проверить роль, грейд, prerequisites по текущим навыкам, добровольность и сессию на дату среза или позже; self-paced доступен без сессии. Несоответствие любого обязательного условия исключает событие до вызова LLM. Допуск прошлых записей истории не переоценивается по нынешнему грейду. |
| D06 | Повторное добровольное участие | Завершённое добровольное событие не рекомендуется повторно, кроме `EV_036`. Исключение допускает новое участие, но не повторное начисление за одну и ту же запись. Незавершённое участие не создаёт дубликат активной записи. Правило не удаляет повторные обязательные назначения из импортной истории. |
| D07 | Нулевой полезный рост и потолок | Показать фактическую прибавку с учётом cap; не обещать «+1», если уровень уже выше cap. Событие без вклада в заявленную цель не выдавать как закрывающее её разрыв. |
| D08 | Траектория | Без явной цели — порядок Junior → Middle → Senior → Lead; валидная `career_goal` задаёт выбранную цель. Разрыв `max(0, required − current)`, critical skills выделены отдельно. Достижение требований не повышает грейд автоматически. Другую карьерную цель не смешивать с требованиями следующего грейда текущей роли; её выбор не обходит допуск по текущей роли. |
| D09 | Завершение и свежесть | В одной транзакции фиксируются завершение и его последствия; версия профиля/рекомендаций меняется. Старые рекомендации помечаются устаревшими и не обещают уже достигнутый рост. Параллельный повтор не даёт двойной награды. |
| D10 | Импорт валидного пакета | Основной формат JSON — `{meta, employees: [...]}`; CSV — колонки кита. Голый массив не подменяет формат кита и допустим лишь как отдельно документированный адаптер. Ссылки разрешаются в существующих данных и внутри пакета; ошибки содержат файл, строку/поле и причину. Валидация предшествует записи. |
| D11 | Импорт с ошибкой | Неверный уровень, дата, статус, неизвестный skill/event/employee или отсутствующая в каталоге комбинация роли/грейда профиля отклоняют весь пакет. После отказа количество записей и версия данных не меняются. |
| D12 | Повтор и конфликт импорта | Тот же пакет и идентичные записи не дублируются. Совпадающий ID с отличающимися данными — явный конфликт, без молчаливой перезаписи. Отдельно проверить повтор после потери сетевого ответа. |
| D13 | Повторные обязательные назначения | Импорт сохраняет distinct `record_id` для обязательного события после предыдущего completed, включая новый completed и overdue. Не дедуплицировать по `(employee_id,event_id)` и не отклонять по правилу неповторяемости voluntary. В исходном ките таких повторных строк 544 для `EV_001/EV_002/EV_003`: 474 completed и 70 overdue; их сохранность проверяется агрегатами. |

Решения о proxy даты, транзакциях, состояниях и конфликтах — проектные правила, а не дополнительные утверждения ТЗ. Их ограничения должны оставаться в README реализации.

## Приёмка AI

LLM получает подготовленные сервером факты профиля и допустимых событий. Она выбирает и объясняет, а сервер проверяет ответ. Отклонённый ответ не публикуется пользователю.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| L01 | Конфликт минимального навыка и карьерного приоритета | У синтетического сотрудника Public Speaking ниже всех, но история содержит три пропуска похожих активностей; System Design критичен для следующего грейда. Рекомендация учитывает этот конфликт и предлагает достижимый шаг к критическому разрыву с подтверждённым объяснением. |
| L02 | История меняет подход | Сравнить два одинаковых профиля с разной историей участия. Рекомендации или обоснованный способ участия учитывают различия; пропуски не трактуются как диагноз или доказательство нежелания развиваться. |
| L03 | Желательный, но недоступный шаг | Событие лучше всего закрывает critical skill, однако prerequisites или аудитория не подходят. Оно не попадает в ответ; предлагается другой допустимый шаг с положительным сокращением текущего целевого разрыва, если он есть. Цепочки prerequisites вне текущих целевых разрывов — расширение после MVP; при отсутствии прямого шага вернуть `no_candidates`. |
| L04 | Неизвестные профили жюри | Прогнать три новых профиля и CSV через настоящий импорт; никаких ветвлений по известным employee ID. На каждом проверить допустимость, факторы и арифметику. Утверждать знание скрытых профилей нельзя. |
| L05 | Галлюцинации и неверный формат | Ответ с неизвестным/недопустимым ID, дубликатом, более чем тремя шагами, неверным gain, выдуманной историей или недостающими доказательствами отклоняется валидатором. |
| L06 | Инструкции внутри данных | Текст события или профиля «игнорируй правила» остаётся данными. Модель не получает секреты; выход не обходит список допустимых ID и серверные проверки. |
| L07 | Сбой модели | Таймаут, 429/5xx и невалидный ответ переводят запрос в объяснимый fallback в общем лимите 10 с. Источник рекомендации виден: AI или резервный алгоритм; fallback не представляется успешным LLM-вызовом. |
| L08 | Пустые и неполные состояния | Доменные причины: `no_target` (нет цели), `target_satisfied` (все разрывы закрыты), `no_candidates` (нет прямого допустимого шага), `insufficient_evidence` (нет кандидата с тремя проверяемыми категориями). Отдельно хранить состояния UI/запроса `not_generated`, `stale` и ошибку провайдера/fallback. При пустом доменном результате LLM не вызывается, `source=none`, `empty_reason=planning_state`. Отсутствие истории — отсутствие сведений, а не низкая вовлечённость. |

Для L01–L04 нужен рубрикатор, а не сравнение свободного текста с эталоном: допустимость ID, вклад в целевые навыки, учёт critical skills, учёт истории, минимум три проверяемых фактора, отсутствие неподтверждённых фактов. Отдельно сохраняются время, версия prompt/модели, входная версия профиля и результат валидатора без секретов и полного датасета.

## Порядок прогонов и готовность к защите

1. Участник 2 проверяет D01–D13 и права на синтетических fixtures; сохранность исходного кита сверяет агрегатами локально. Владелец проверяет L01–L08 независимо от UI на подготовленном контракте.
2. Участник 3 проходит A01–A06 сначала на общем mock, затем с реальным API. Mock явно обозначен и не считается доказательством работающего backend/AI.
3. Владелец проходит полный цикл: импорт → профиль → рекомендация → выполнение → обновлённая траектория → HR; отдельно отрицательные сценарии прав, импорта и LLM.
4. Второй участник команды воспроизводит запуск с чистой копии. В отчёте фиксируются commit, окружение, сценарии, pass/fail и известные ограничения. Не пройденные тесты не отмечаются выполненными.

|---|---:|---|
| Соответствие и работоспособность | 25 | Живой основной цикл A01–A06, включая новый профиль жюри |

| Потенциал и оригинальность | 10 | Проверяемые объяснения, расширяемые адаптеры/политики; опциональные функции явно отделены от работающего MVP |
