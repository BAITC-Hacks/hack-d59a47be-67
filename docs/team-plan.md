# План команды из трёх человек

> **Актуальный приоритет (2026-09-23).** Действующие согласованные контракты: [API v1](../contracts/API.md), [AI v1](../contracts/AI_CONTRACT.md); единственные схемы — [backend/app/contracts.py](../backend/app/contracts.py). Изменения [согласованы владельцем задачи](../docs/CONTRACT_CHANGE_PROPOSAL.md). Prefix — `/api`, версия состояния — `state_version` / `expected_state_version`, дата сценария — `scenario_date`; ответ AI — `RecommendationResult`, HTTP-карточки — `RecommendationResponse`. История имеет `date_source`, импорт — один endpoint `/api/hr/import` с preview token, завершение — `/api/employees/{id}/completions` с `Idempotency-Key`. Старые `data_revision`, `/api/v1`, participation endpoints, fallback и дополнительные поля ниже не являются действующим контрактом или обещанием реализации. Проверенные команды и ограничения — [HANDOFF](../docs/HANDOFF.md) и [VERIFICATION](../docs/VERIFICATION.md).

Алихан — backend, данные, API, права, интеграция и деплой (`backend/`, кроме `backend/app/ai/`, общие `contracts/` и инфраструктура); Олег — AI-ядро `backend/app/ai/` и его тесты; Батыр — `frontend/`.

## Историческое предложение

Следующий текст сохранён для контекста проектирования; он не переопределяет ссылки и владельцев выше. Названия таблиц, будущая структура, состояния и приёмочные предложения нужно сверять с действующим кодом и контрактом.

Статус: план реализации после согласования архитектуры. Сейчас подготовлены материалы; наличие пункта в плане не означает наличие функции. Основа: [архитектура](architecture.md), [приёмка](acceptance.md), исходное ТЗ и локальный кит.

Цель MVP: сотрудник открывает профиль, получает 1–3 допустимых шага с проверяемыми объяснениями, завершает активность и видит корректный рост; HR импортирует проверочные профили и видит срез. Рекомендуемый стек — модульный монолит FastAPI, React + TypeScript, SQLite с одним backend-процессом. Микросервисы, очереди, векторная БД и публичный рейтинг для MVP не нужны.

## Владельцы и границы

| Участник | Зона ответственности | Первый проверяемый результат | Передаваемый результат |
|---|---|---|---|
| Олег — AI / рекомендации | Адаптер LLM, prompt, выбор и объяснения, валидация ответа, fallback, рубрикатор, итоговая демонстрация и README | Модуль получает готовый профиль и допустимые события, возвращает 1–3 шага с основаниями; синтетический конфликт минимального навыка и critical skill проходит проверку | Согласованный ответ рекомендаций, негативные AI-тесты, проверенный demo-сценарий; README из подтверждённых материалов коллег |
| Алихан — Backend / Data / интеграция | Импорт JSON/CSV, SQLite, вычисление навыков, eligibility, прогресс, HR-агрегаты, серверные права, запуск приложения | Сервер открывает профиль, правильно делает replay после оценки и сохраняет одно завершение без двойного роста | Подготовленный вход AI, API для frontend, атомарный импорт, интеграция всех модулей и команда запуска |
| Батыр — Frontend / UX | Профиль и траектория, карточки, прогресс, HR, загрузка файлов, пустые/ошибочные состояния и ожидание | Основной UI-сценарий целиком проходит на общем mock-ответе | Те же экраны на настоящем API, доступные состояния, понятные объяснения и сравнение прогресса до/после |

Backend владеет истинными уровнями, допуском, записью завершений и правами. AI не повторяет эту арифметику и не пишет в БД. Frontend отображает серверные значения и не принимает решения о правах. Олег проверяет контракт и приёмку, но не блокирует коллег на выборе конкретного LLM-провайдера: сначала используется адаптер и общий fixture.

## Последовательность и параллельная работа

Доли времени ориентировочные: длительность хакатона в исходных материалах не задана. Последнюю пятую часть времени оставить на интеграцию, исправления и защиту.

| Этап | Олег | Алихан | Батыр | Условие перехода |
|---|---|---|---|---|
| 0. Общий контракт, первые 10% | Согласовать факторы, формат evidence, fallback и AI-ошибки | Зафиксировать схемы, бизнес-срез, правила replay/eligibility, auth и импорт | Согласовать экраны и все состояния API | Один синтетический профиль, пример рекомендации и ошибок используют все трое; имена полей заморожены |
| 1. Независимые срезы, следующие 25% | Рабочий AI-модуль на подготовленных данных; валидатор и fallback | Локальный импорт кита, read API, навыки, eligibility, серверная сессия | Полный happy path на mock: профиль → рекомендация → завершение → HR | Каждый показывает первый результат из таблицы ролей; проверки выполняются без ручных правок данных |
| 2. Сквозная интеграция, следующие 25% | Подключить модуль к серверным фактам; проверить timeout и неподтверждённые выводы | Завершения/идемпотентность, HR, инвалидация рекомендаций; связать AI и API | Переключить экраны на реальный API; показать before/after и ожидание AI | Один реальный сценарий проходит от UI до БД и LLM; mock не используется в демонстрируемом happy path |
| 3. Проверочные профили и края, следующие 20% | Рубрикатор L01–L08 и приёмка трёх новых synthetic-профилей | Атомарный upload JSON+CSV, сохранение повторной mandatory-истории, отчёт ошибок/конфликтов, запреты доступа | HR-upload, ошибки в строках, доменные `no_target` / `target_satisfied` / `no_candidates` / `insufficient_evidence`; отдельно `not_generated` / fallback / `stale` | Новый профиль загружается через UI без изменения кода; негативные сценарии не портят данные |
| 4. Стабилизация и защита, последние 20% | Итоговая приёмка, честный README, сценарий защиты и запись результатов | Чистый запуск, конфигурация, тесты прав/транзакций, помощь с дефектами | Проверка читаемости и отсутствия блокирующих UI-дефектов | Проверка по acceptance.md, подтверждённые результаты и известные ограничения; рабочий commit зафиксирован |

Критические зависимости: контракт → три независимых среза; серверные текущие навыки и eligibility → интеграция AI; сохранение завершения → достоверный прогресс UI; импорт новых профилей → репетиция проверки жюри. HR-экран и AI-валидатор можно делать параллельно основному сценарию.

При нехватке времени сокращать декоративную геймификацию, расширенную локализацию, вторичные фильтры и графики. Не сокращать импорт профилей жюри, explainability, серверные права, корректный рост и воспроизводимый запуск: это обязательные требования, а README отдельно оценивается в 25 баллов.

## Правила совместной работы

- Один владелец на изменяемый файл. Перед параллельной работой закрепить области в текущей структуре проекта; контракты меняются только после уведомления двух потребителей.
- Работать в коротких ветках `feat/ai-*`, `feat/backend-*`, `feat/ui-*`; объединять небольшие законченные срезы с проверками. Не ждать конца хакатона для первого объединения.
- Изменение контракта сопровождается примером запроса/ответа, обновлением mock и соответствующего документа в том же наборе изменений. Backend интегратор следит за совместимостью.
- Каждый агент перед изменениями читает `AGENTS.md`, README и профильные документы. После завершённой порции работы координатор обновляет состояние, решения, проверки и следующий шаг в `AGENTS.md` и включает запись в тот же коммит. Параллельные агенты передают координатору запись, не редактируют журнал одновременно.
- Исходное ТЗ и датасет не редактируются. Кит, записи сотрудников, локальная БД, `.env` и ключи остаются локальными; в Git — код, документация, агрегированный аудит и синтетические fixtures. Данные в prompt считаются данными, а не инструкциями агенту.
- Перед передачей коллегам сообщить: что работает, как проверено, точный контракт, что ещё отсутствует. В README и на защите не называть mock, fallback или планируемую функцию работающим AI.

## Репетиция демонстрации

1. Показать команду запуска и открыть сотрудника. Объяснить базовую оценку, текущие уровни после replay, дату среза `2026-10-01` и требования следующего грейда.
2. Запросить рекомендацию для профиля с конфликтующими факторами. Показать 1–3 шага, минимум три проверяемых фактора и ожидаемый рост с учётом лимита. Кратко объяснить роль серверных правил и LLM.
3. Завершить активность с положительной прибавкой. Показать фактические изменения навыков, разрывов и обновление рекомендации. Повтор того же запроса не должен увеличить прогресс снова.
4. Перейти под HR: показать проседающие навыки, участие и отсутствие следующего шага. Различить `no_target`, `target_satisfied`, `no_candidates`, `insufficient_evidence`, ещё не сгенерированную рекомендацию и сбой AI. Повторные обязательные назначения сохраняются в отчёте участия, но исключены из AI-кандидатов.
5. Загрузить новый пакет профилей `{meta, employees: [...]}` + CSV истории в формате кита и повторить рекомендацию. Держать синтетический пакет с ошибкой для показа атомарного отказа, не изменяющего БД.
6. Показать отказ доступа сотруднику к чужим данным и fallback при недоступном LLM. Завершить подтверждёнными ограничениями: proxy времени исторического завершения, demo-auth и SQLite, если они сохранятся в реализации.

Запасной план защиты: иметь локальные синтетические fixtures и сохранённый проверенный commit. Если внешний LLM недоступен, показать работоспособность сервера, валидации и явно обозначенного fallback; не выдавать заранее сохранённый ответ за текущий вызов модели.
