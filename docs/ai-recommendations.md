## Граница ответственности

| Backend / Data — Алихан | AI — Олег | Frontend / UX — Батыр |
|---|---|---|
| Импорт, авторизация, текущие навыки, цель, разрывы, доступность событий, прогноз прироста, факты и ревизия данных | Выбор 1–3 из переданных кандидатов; prompt и adapter; проверка ответа совместно с backend; fallback; приёмочные сценарии | Состояния загрузки, карточки, объяснения и пустые состояния; явная маркировка резервного алгоритма |
| Только backend изменяет историю и начисляет навыки в транзакции | Модуль возвращает ссылки на факты; не начисляет навыки и не назначает новый грейд | Интерфейс отправляет команды, но не считает прогресс самостоятельно |

AI-модуль не читает БД напрямую, не выполняет tools/function calls и не имеет сетевых действий кроме выбранного adapter. Его вход — подготовленный контекст. Модель не решает, разрешено ли событие, не вычисляет уровни и не принимает решения о повышении сотрудника.

## Контракты и направление данных

1. Backend строит [`recommendation-context.schema.json`](../contracts/recommendation-context.schema.json): `context_id`, `data_revision`, `policy_version`, `as_of_date`, `employee`, `target`, `planning_state`, `candidates`, `evidence`.
2. Для `planning_state=actionable` adapter передаёт контекст модели с ограниченным выводом. Точный shape ответа — `$defs/modelOutput` из [`recommendation-result.schema.json`](../contracts/recommendation-result.schema.json): `{context_id, recommendations: [{event_id, rank, evidence_ids}]}`. JSON Schema является provider-neutral Draft 2020-12; при ограничениях structured output провайдера adapter преобразует схему, а локальный валидатор всё равно проверяет исходную.
3. Сервер проверяет структуру **и семантику** ответа. Затем сам добавляет `schema_version`, `data_revision`, `policy_version`, `status`, `source`, `fallback_reason`, `empty_reason`. Модель не может объявить свой ответ проверенным или скрыть fallback.
4. UI API обогащает результат названием события и локализованным объяснением из проверенных фактов. Модель не возвращает свободный narrative, даты, прогнозы, уровни или тексты причин. Они не входят в контракт результата.

Контракт AI-модуля — внутренний; браузер не отправляет готовый контекст и не определяет `employee_id` текущей сессии. Сервер проверяет права до подготовки контекста и до выдачи кэшированного результата. Идентификаторы в примерах `FIX_*` и роль `Fixture Platform Specialist` целиком вымышлены; записи исходного кита в fixtures не копируются.

## Подготовка контекста

Backend восстанавливает текущие навыки от оценки в `last_review_date`, применяя только ещё не учтённые `completed` после неё по согласованному порядку. Для исторического CSV нет отдельного completion timestamp: трактовка его `date` как даты применения завершённой записи — явно документированное допущение backend, одинаковое при replay и импорте. Отсутствующий в профиле навык из каталога имеет уровень 0; неизвестный каталогу skill_id — ошибка импорта. Рост ограничен правилом события: `new = max(current, min(current + gain, max_level, 5))`; навыки не уменьшаются при низком `max_level`. AI получает итог, а не поручение пересчитать историю.

Цель задаёт backend: явный `career_goal`, иначе следующий грейд текущей роли. Для Lead без явной цели — `target=null`. Допустимость цели и перехода роли относится к отдельной backend-политике, а не к свободному выбору LLM.

До AI исключаются обязательные события, неподходящие текущей роли/грейду, недоступные по prerequisites, уже завершённые невозобновляемые события, уже начатые активности и события без доступной сессии. Исключение повторяемости регулярного клуба из кита задаётся конфигурацией политики. `self_paced` доступен без даты; для остальных используется ближайшая разрешённая дата `>= as_of_date`. Eligibility не расширяется по желаемой будущей роли. Формат сам по себе не является запретом для remote-сотрудника: из рабочего формата нельзя вывести жёсткое ограничение участия.

Запрет повторного предложения относится к добровольным кандидатам, а не к удалению исторических записей: в ките есть повторные обязательные назначения после `completed`. Импорт сохраняет эти попытки; обязательные мероприятия в любом случае исключены из AI-рекомендаций.

В `candidates` входят события с положительным эффективным приростом и положительным сокращением хотя бы одного разрыва цели. Переходы через prerequisites, которые не сокращают текущий целевой разрыв, остаются последующим расширением; MVP возвращает честное `no_candidates`, если прямых шагов нет. На странице каталога могут отдельно отображаться другие добровольные активности. Каждая рекомендация прогнозируется от одной исходной ревизии: три карточки — альтернативы следующего шага, их приросты нельзя суммировать как уже рассчитанный последовательный план.

`projected_gains` содержит все положительные приросты события; `target_gap_reduction` для навыка вне цели равен 0. В `evidence` четыре типизированные категории:

| Категория | Подтверждённое основание |
|---|---|
| `grade` | Текущие роль/грейд входят в аудиторию события |
| `skill_gap` | Текущий уровень, требуемый уровень, разрыв, эффективный прирост и сокращение разрыва |
| `target_requirement` | Требование целевой роли/грейда и признак критичного навыка из каталога |
| `history` | Проверенные количества статусов по событию или сочетанию типа и формата, с окном и размером выборки |

Минимум **три различные категории на каждую карточку**, обычно все четыре. Три ссылки из одной категории не выполняют условие. `skill_gap` и `target_requirement` должны относиться к навыку, который событие действительно развивает и по которому остаётся разрыв. Нулевая история — явный факт `sample_size=0`, а не утверждение о предпочтении. Она не мешает получить рекомендацию.

## Многофакторный выбор

Цель — полезный достижимый шаг. Самый низкий абсолютный навык не обязательно блокирует целевой грейд. Критичность берётся из `critical_skills` целевого профиля, а не придумывается моделью. Для события backend считает:

```text
gap(s) = max(0, required(s) - current(s))
reduction(s, event) = min(gap(s), effective_gain(s, event))
critical_gap_gain = sum(reduction for critical target skills) / sum(positive critical gaps)
target_gap_gain = sum(reduction for target skills) / sum(positive target gaps)
history_fit = (completed - dropped - no_show - declined) / (sample_size + 2)
effort_cost = min(duration_hours / 40, 1)
score = 0.60 * critical_gap_gain + 0.25 * target_gap_gain
      + 0.12 * history_fit - 0.03 * effort_cost
```

Если знаменатель для `critical_gap_gain` равен 0, значение равно 0. При нулевой истории `history_fit=0`. `sample_size` — сумма всех шести счётчиков статусов; история ограничена окном из контекста. В `heuristic-v1` оно совпадает с доступным периодом кита. Для сравнимости `history_fit` считается по сочетанию типа и формата для каждого кандидата; факты по конкретному событию могут дополнительно объяснять выбор, но не заменяют правило скрытым образом.

Это **настраиваемая, версионируемая эвристика**, а не обученная модель, вероятность завершения или доказанная оценка сотрудника. Константа 40 часов, веса, окно истории и штраф разнообразия — стартовые решения команды; менять их можно по результатам приёмки с новой `policy_version`. История пропусков означает неопределённость формата, а не лень, низкую ценность сотрудника или основание отказать в развитии.

Для обычной цели backend проверяет правило опорного шага: если среди кандидатов есть сокращающий критичный разрыв, рекомендация ранга 1 должна сокращать такой разрыв. Это делает критичный навык приоритетным даже при низком другом навыке. В пределах этого ограничения LLM сопоставляет историю, пользу и нагрузку; score передаётся через его составляющие как ориентир. Негативная история не блокирует критичный шаг автоматически: при возможности выбирается другой тип/формат работы с тем же навыком.

После первого шага допускаются ещё до двух альтернатив. Fallback выбирает первый по максимальному score среди кандидатов опорного шага; затем по положительному marginal score `score - 0.10 * max_overlap`, где overlap — Jaccard-мера множеств целевых навыков с положительным сокращением разрыва между кандидатом и уже выбранными карточками. При равенстве — `event_id` по возрастанию. Дубли event_id запрещены. Если все score неположительные, первая допустимая карточка всё равно предлагается с честным обоснованием; дополнительные добавляются только при положительном marginal score. LLM может выбрать другое число 1–3, но не обходить eligibility, критичный опорный шаг и требования к доказательствам. Разнообразие форматов желательно при близкой пользе; фиксированной квоты нет.

В синтетическом примере критичный `FIX_SKILL_PATH=2` при требовании 4 и положительная история онлайн-менторства перевешивают минимальный `FIX_SKILL_TALK=0` и три пропуска офлайн-воркшопов. Пример результата помечен `source=fallback`: он не является результатом реального AI-вызова.

## Проверка ответа и безопасное объяснение

JSON Schema проверяет типы, ограничения, перечисления и отсутствие лишних полей. Отдельный semantic validator обязан проверить:

1. Ровно тот же `context_id`; ревизия всё ещё актуальна; 1–3 различных event_id из кандидатов.
2. Ранги уникальны, идут подряд `1..N`, список отсортирован по рангу.
3. Все evidence_id существуют, перечислены в `candidate.evidence_ids`, относятся именно к выбранному event_id и покрывают минимум три категории. Ссылки на чужую карточку запрещены.
4. Факты согласованы с `employee`, `target`, `projected_gains` и первичными доменными расчётами. Суммы history-счётчиков равны `sample_size`; даты окна корректны; уровни и разрывы согласованы. Evidence не является источником истины сам по себе.
5. Соблюдено правило критичного опорного шага. В результате отсутствуют неразрешённые ключи и произвольный текст.
6. Eligibility и право доступа сохраняются на момент выдачи; после изменения состояния результат не применяют к старой ревизии.

Несуществующая ссылка, подмена контекста или слабое обоснование инвалидируют весь model output. Не исправлять чужие ID догадкой и не выдавать частично проверенный ответ. Детерминированный fallback проходит тот же валидатор. При внутренне неконсистентном контексте — контролируемая ошибка backend, а не успешная рекомендация.

Объяснение рендерится шаблонами сервера из разрешённых полей. Например: «Активность подходит вашему грейду Middle. Навык Design Lab: 2 из требуемых 4 для Senior; после завершения ожидается 3. Это критичный навык цели. В сравнимых онлайн-активностях: 2 завершения из 2 записей». Название навыка берётся из серверного каталога; текст экранируется. Не писать «в срок»: для добровольных событий в ките нет due_date. Не писать «после курса вы станете Senior»: прогноз навыка не является обещанием повышения.

Ссылки на факты — проверяемый след принятого решения, не chain-of-thought. Не запрашивать или сохранять внутренние рассуждения модели.

## Пустые состояния и сбои

| Состояние контекста | Поведение |
|---|---|
| `actionable` | Вызов AI; проверка; 1–3 результата или помеченный fallback |
| `target_satisfied` | Все разрывы цели равны 0; `status=empty`, список пуст; предложить обсудить следующую цель, не присваивать грейд |
| `no_target` | Lead без явно заданной цели; пустой результат, никакого выдуманного следующего грейда |
| `no_candidates` | Цель есть, разрывы есть, прямых допустимых событий нет; UI объясняет состояние, HR видит пробел каталога |
| `insufficient_evidence` | Допустимые события есть, но ни одно не получило три достоверные категории; пустой результат и диагностическая причина |

Для пустого состояния `source=none`, `empty_reason=planning_state`, `fallback_reason=null`; LLM не вызывается. `candidates` и `evidence` в таком контексте пустые. Приоритет состояний: `no_target` → `target_satisfied` → `no_candidates` → `insufficient_evidence` → `actionable`. Диагностика отсеянных событий хранится backend отдельно от минимального AI-контракта.

При timeout, недоступном провайдере или невалидном ответе используется `source=fallback` с причиной `timeout`, `provider_unavailable` или `invalid_output`. UI показывает «Резервный алгоритм»; отсутствие AI нельзя представлять работающей AI-рекомендацией. Указанные состояния входят в нормальный продуктовый сценарий; HTTP 500 для Lead или отсутствия мероприятий не нужен.

## Задержка, кэш, границы данных

Бюджет endpoint — 9,5 с по monotonic deadline: до 0,6 с на чтение и подготовку, один model request с пределом 7 с, до 0,3 с на проверку/fallback, до 0,4 с на сборку ответа, остальное резерв. Повторного model request на пути пользователя нет. Если осталось недостаточно времени, сразу fallback. Это проектная цель, которую необходимо измерить; сейчас latency не подтверждена. Профиль загружается отдельно, интерфейс показывает AI-loading без блокировки остального экрана; целевой отклик UI ≤2 с.

Ключ кэша включает employee_id, data_revision, as_of_date, policy_version, schema_version, prompt_version и идентификатор конфигурации model adapter. `data_revision` атомарно меняется при импорте, завершении активности, смене оценки, цели или каталога. Смена даты среза тоже меняет ключ. Локализованные тексты рендерятся после кэша; если кэшируется готовый UI-response, его ключ дополнительно включает locale. Проверка прав всегда предшествует lookup. TTL ограничивает хранение, но не заменяет ревизию. Старый результат после завершения активности игнорируется; backend перестраивает контекст.

В model payload отсутствуют имя, email, manager_id и полные строки истории; остаются минимальный профиль и агрегаты для одного сотрудника. Это уменьшение данных не отменяет ограничения кита: исходные данные не выносятся за пределы хакатона. Для интеграции по умолчанию — локальный model adapter либо полностью вымышленные fixtures. Облачный adapter можно включать только в разрешённом организаторами контуре; сейчас передачи данных во внешнюю AI-систему не производится. Логи содержат версии, длительность, source, коды ошибок и идентификатор запроса, без сырого prompt, истории и ответа.

## Первый проверяемый результат владельца AI

Согласовать эти схемы с backend/frontend и реализовать один вызываемый модуль `recommend(context) -> result`, состоящий из adapter, semantic validator, fallback и renderer. На вход — JSON по контракту, на выход — 1–3 проверенные рекомендации или документированное пустое состояние. Live model run и fallback должны различаться в записи приёмки. До подключения модели frontend может работать с полностью вымышленным [`recommendation-result.json`](../contracts/examples/recommendation-result.json).

Критерии приёмки модуля:

- Контрольный конфликт: минимальный некритичный навык с пропусками против критичного разрыва с подходящей альтернативой; опорный шаг закрывает критичный разрыв.
- Отсутствующая история остаётся нейтральной; истории по одному человеку недостаточно для утверждения о постоянных предпочтениях.
- Обязательное, уже завершённое, начатое, закрытое по prerequisites или расписанию событие не возвращается; повторяемое исключение применяется только backend-политикой.
- Для каждой карточки проверяются ≥3 категории, принадлежность фактов и точные числа; выдуманный ID, три одинаковые категории, несовпадающий context_id, дубли и ложные ранги отклоняются.
- При нулевых разрывах, Lead без цели и нулевых кандидатах возвращаются отдельные пустые состояния без AI-вызова.
- Таймаут, сломанный JSON и попытка инструкции в названии импортированного события не обходят проверку; fallback явно помечен.
- Завершение активности повышает data_revision и меняет контекст; повторная команда не начисляет прирост дважды. Это интеграционная проверка с backend, не вычисление модели.
- На защите дополнительные профили/история импортируются без правок prompt и без hardcode employee_id. Один реальный разрешённый model call, его latency и валидность результата подтверждаются отдельно от fixture-проверок.
