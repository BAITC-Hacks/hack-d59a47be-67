# Аудит стартового кита Career Quest

Дата аудита: 2026-09-23. Источник: локальный `career_quest_dataset.zip`, семь
неизменённых файлов в `data/raw/`, README кита на EN/RU/KZ. Назначение проверки:
спроектировать импорт, расчёт навыков, допустимые рекомендации и HR-показатели.
Это аудит синтетического снимка; оценки не описывают реальную компанию.

**Вывод:** структура и связи пригодны для прототипа. Без явных решений о времени
завершения, повторном compliance и непокрытых навыках система будет уверенно
объяснять недоказуемые результаты. Наличие каталога не гарантирует всем 1–3
активности с полезным ростом.

## Воспроизведение и границы

```bash
python3 scripts/prepare_dataset.py career_quest_dataset.zip
python3 scripts/audit_dataset.py data/raw > /tmp/career-quest-audit.json
python3 -m unittest discover -s tests -p 'test_dataset_tools.py' -v
```

Весь расчёт находится в `scripts/audit_dataset.py`, без внешних зависимостей.
Выход JSON содержит схемы, число проверок, нарушения, распределения и агрегаты,
без строк исходных данных. `scripts/prepare_dataset.py` извлекает ровно семь
разрешённых файлов, проверяет пути, размер, ссылки и коллизии. Архив и raw остаются
локально. Повторное извлечение идентичного кита не меняет файлы.

Объект аудита — поставленный кит, а не ещё не реализованный сервер импорта.
При структурно неподдерживаемом входе аудит прекращается с ошибкой; это не
полная JSON Schema для сообщений пользователю. Производственный импорт должен
давать ошибки с местом в файле и отклонять пакет транзакционно.

## Фактический состав и схемы

Во всех трёх JSON верхний уровень — **объект**, а не массив. В `meta` находятся
`dataset: string`, `version: string`, `as_of_date: date`; значения meta согласованы,
версия `1.0`, дата снимка **2026-10-01**. Считать её «сегодня» — условие симуляции
из README. Это не свежие наблюдения относительно часов машины.

| Таблица | Строк | Гранулярность / ключ |
|---|---:|---|
| `employees.json → employees[]` | 200 | Сотрудник; `employee_id` |
| `events.json → events[]` | 40 | Тип активности; `event_id` |
| `skills.json → skills[]` | 60 | Навык; `skill_id` |
| `skills.json → role_profiles[]` | 32 | Требования роли и грейда; `(role, grade)` |
| `activity_history.csv` | 2 743 | Попытка участия; `record_id` |

`employee_id + event_id` **не** является уникальным ключом истории: попытки
повторяются. Даже `employee_id + event_id + date`, уникальный в этом снимке,
не следует превращать в универсальное ограничение без уточнения модели сессий.

| Объект | Фактические поля и типы |
|---|---|
| Employee | `employee_id`, `full_name`, `department`, `role`, `grade`, `work_format`, `preferred_language`: string; `manager_id`: string/null; `hire_date`, `last_review_date`: ISO date; `tenure_months`: int; `skills`: object `{skill_id: int 0..5}`; `career_goal`: object/null `{target_role: string, target_grade: string}` |
| Event | `event_id`, `title`, `description`, `type`, `format`: string; `duration_hours`: number; `mandatory`: bool; `target_roles`, `target_grades`: string[]; `develops_skills`: `{skill_id: string, gain: int, max_level: int}[]`; `prerequisites`: `{skill_id: int}`; `upcoming_sessions`: ISO date[] |
| Skill | `skill_id`, `name`, `type`, `category`, `description`: string; `type ∈ {hard, soft}` |
| Role profile | `role`, `grade`: string; `required_skills`: `{skill_id: int 0..5}`; `critical_skills`: string[] |
| Proficiency scale | `skills.json → proficiency_scale`: object, строковые ключи `"0"`…`"5"`, строковые описания |
| History | 10 CSV-колонок: `record_id`, `employee_id`, `event_id`, `date`, `due_date`, `status`, `completion_pct`, `score`, `feedback_rating`, `assigned_by`. На входе все значения строки; преобразование обязательно. `due_date`, `score`, `feedback_rating` допускают пустую строку |

Вложенные словари навыков разрежены: отсутствие навыка означает **0**, а не
неизвестное значение. Даты не содержат время или часовой пояс. `upcoming_sessions`
содержит даты, но не session_id, вместимость, регистрацию или локацию.

У навыков 46 hard / 14 soft; у сотрудников 59 Junior / 78 Middle / 47 Senior /
16 Lead. Есть 8 ролей, для каждой все четыре грейда. `career_goal`: 106 той же
роли, 28 другой роли, 66 отсутствует. У 10 Lead цель отсутствует; следующего
грейда выше Lead в каталоге нет.

Из 40 активностей 4 обязательные и 36 добровольных. Форматы: 21 online,
10 offline, 9 self_paced. Типы: 17 workshop, 15 course, 3 compliance,
2 mentoring, по 1 certification/onboarding/meetup. Три compliance не развивают
навыки; обязательный onboarding может развивать навыки, но не является целью
добровольных рекомендаций.

## Выполненные проверки целостности

74 группы проверок, 64 508 проверок отдельных объектов и связей, **0 нарушений**
в поддерживаемых структурных и доменных правилах. Смысловые исключения ниже
отдельно отражаются в JSON и не маскируются этим результатом.

- Нет повторных первичных ключей, полных дубликатов и повторных троек
  `(employee_id, event_id, date)`.
- Все ссылки из employees/history/events/role_profiles на навыки, сотрудников,
  активности и пары роль/грейд разрешаются. Руководители — Lead того же отдела,
  самоссылок нет; `manager_id = null` только у Lead.
- Типы и диапазоны уровней, gain, caps, duration, enum-значения и даты корректны.
  `critical_skills` уникальны и входят в required_skills; требования по грейдам
  не убывают. Стаж совпадает с полными месяцами от hire_date до snapshot.
- История отсортирована; записи после найма и до snapshot. `completed → 100%`,
  `no_show/declined → 0%`, диапазоны остальных статусов соблюдены.
- `overdue` только для обязательной активности с прошедшим due_date;
  `no_show` только для событий по расписанию; `declined` назначен manager/hr.
- Score только у завершённых course/certification/compliance. У таких completed
  нет отсутствующих score. Пустой feedback допустим и не означает низкую оценку.
- Добровольные активности после completed не повторяются, кроме клуба EV_036.

Историческое соответствие прошлой роли, грейду и prerequisites **не доказано**:
README обещает его, но таблиц прошлых назначений и оценок нет. Сравнение прошлой
записи с сегодняшним профилем не является проверкой нарушения.

freshness/drift между поставками проверить нельзя.

## Восстановление навыков: источник и принятая для аудита гипотеза

**Факты README:** employee.skills — результат последней оценки; completed после
`last_review_date` ещё не включены. Growth задаётся gain и max_level события.
Остальные статусы навыки не меняют. Отсутствующий навык равен нулю.

**Расчётная гипотеза аудита:** при импорте использовать history.date как
приближение даты завершения, строго `last_review_date < date <= as_of_date`.
Это необходимо помечать provenance `completion_date_proxy`, поскольку date для
self_paced означает регистрацию/назначение. Даже для scheduled-сессии отдельной
даты фактического завершения нет. На дату review включение не доказано; четыре
completed в такой день исключены по буквальному «после».

Воспроизводимый порядок replay: `(date, record_id)`; для каждой пары навык/growth:

```text
after = max(before, min(5, event.max_level, before + event.gain))
delta = after - before
```

Формула не снижает уже имеющийся уровень выше cap. По этой гипотезе:

- 1 860 из 2 178 completed находятся до или в день review и не переигрываются.
- 318 completed после review у 133 сотрудников; у 111 навыки реально изменяются.
- 139 из 318 относятся к self_paced: время регистрации не доказывает время
  окончания. Число ошибочно отнесённых к baseline более ранних регистраций
  определить нельзя.
- 308 отдельных положительных изменений навыка; 132 completed не дают роста
  (нет развиваемых навыков либо достигнут cap).
- В 11 применениях growth уже имевшийся уровень выше cap. Без внешнего max
  ошибочный расчёт снизил бы навык после обучения.

**Рекомендация архитектуре:** хранить неизменный baseline + журнал завершений;
перестраивать snapshot или использовать идемпотентный skill ledger. Импорт
record_id не должен второй раз начислять прирост. Для новых действий приложения
добавить реальный `completed_at`; не путать его с scheduled/enrolled_at. Не
начислять дополнительный бонус за score: такого правила в ките нет.

## Доступность и покрытие каталога

**Факты каталога:** 72 growth-правила, буквальных `gain = 0` нет. Но один навык,
`SK_TEST_DESIGN`, не развивается вообще. Для 13 пар «role_profile + skill»
требование выше максимального cap любых добровольных активностей; одна из этих
пар критическая. Затронуты 8 навыков: SK_CLOUD, SK_COMMUNICATION,
SK_COMPENSATION, SK_EMOTIONAL_INTELLIGENCE, SK_HR_ANALYTICS,
SK_STAKEHOLDER_MGMT, SK_TEST_DESIGN, SK_UX_RESEARCH. Это ограничение каталога;
фактическая доступность по роли/prerequisites может сделать покрытие ещё хуже.

**Принятая политика архитектуры**, не исходное правило заказчика:
кандидат добровольный; текущая роль и текущий грейд входят в аудиторию; все
prerequisites выполнены по восстановленным навыкам; есть будущая сессия либо
self_paced; нет completed (кроме EV_036) и нет открытого in_progress по событию.
Пропуски влияют на ранжирование, но не становятся вечным запретом. Work_format
не даёт жёсткого запрета offline: географии и возможности поездки нет.

Цель в расчёте: явная career_goal, иначе следующий грейд той же роли; для Lead
без цели `target=null`, состояние `no_target`. Такие 10 сотрудников включены в
каталожные показатели, но исключены из расчётов целевых разрывов и рекомендаций.

| Результат при этой политике | Количество |
|---|---:|
| Допустимые пары сотрудник/событие | 1 126 |
| Из них без какого-либо положительного прироста | 60 (5,3%) |
| Из них сокращают хотя бы один разрыв целевой роли/грейда | 461 |
| Сотрудники без допустимой активности до проверки полезности | 0 |
| Сотрудники без активности с положительным приростом | 5 (2,5%) |
| Сотрудники с выбранной/выведенной целью | 190 |
| Сотрудники с разрывами, но без активности, сокращающей их | 31 из 190 (16,3%) |
| Сотрудники хотя бы с одним не покрытым сейчас целевым разрывом | 189 из 190 (99,5%) |

Итоговые состояния рекомендаций, сумма — 200 сотрудников:

| Состояние | Сотрудники | Значение |
|---|---:|---|
| `no_target` | 10 | Lead без явной цели |
| `target_satisfied` | 0 | Все требования выбранной цели выполнены |
| `no_candidates` | 31 | Цель есть, разрывы остались, прямых полезных шагов нет |
| `actionable` | 159 | Есть хотя бы один допустимый шаг с сокращением целевого разрыва |

Не покрытый **сейчас** разрыв может стать доступен после prerequisite; это не
доказательство полной недостижимости. Глобальная нехватка cap отдельно выше.
У 26 сотрудников включение в аудиторию ещё и целевой роли расширяет кандидатов.
Это показывает влияние политики смены роли; допуск в чужую роль требует
явного продуктового решения. Нельзя одновременно показывать эти числа как
результат политики «текущая ИЛИ целевая роль».

Возврат `no_candidates` с конкретными причинами
корректнее выдуманной активности или рекомендации с нулевым ожидаемым эффектом.
HR должен видеть нехватку каталога отдельно от низкого участия человека.

## Смысловые проблемы и решения

| Наблюдение | Риск / важность / уверенность | Минимальное действие |
|---|---|---|
| Нет completed_at; 139 replay-завершений self_paced имеют только дату регистрации | Высокая; факт достоверен, точность reconstructed skills ограничена | Документированный proxy для legacy, реальное время для новых действий; не заявлять завершение в срок |
| 544 попытки обязательных EV_001/002/003 идут после прошлой completed; из них 474 completed и 70 overdue | Средняя; достоверное противоречие общему запрету повтора в README. Вероятное объяснение — ежегодный compliance | Сохранить попытки; исключить mandatory из рекомендаций; запрет повторения применять к voluntary, EV_036 оставить повторяемым |
| 31 из 190 человек с целью без сокращающего target gap кандидата; 5 из всех 200 без роста даже в доступном каталоге | Высокая для качества рекомендации; числа зависят от указанной политики | Явное пустое состояние и причины; не гарантировать три карточки |
| SK_TEST_DESIGN отсутствует; 13 требований выше cap | Высокая для траектории; факт достоверен | HR catalog gap; не обещать закрыть все разрывы этим каталогом |
| 28 cross-role goals, 10 Lead без цели | Средняя; факт достоверен | Согласовать цель и audience policy; не выбирать несуществующий следующий грейд |
| Нет role/grade history, session identity, capacity, завершения в срок | Средняя; факт достоверен | Не вычислять недоказуемые показатели; расширять внутреннюю модель, сохраняя входную схему |

Эти данные не содержат эталонных «правильных рекомендаций». Проверять AI нужно
на синтетических сценариях с известными gap/history/critical constraints,
валидировать event_id, числа и факторы объяснения на сервере. Обучение модели
или оценка её точности по этим 200 профилям без разметки не обоснованы.
